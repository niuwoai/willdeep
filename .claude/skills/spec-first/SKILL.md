# 先写文档，再写代码

这套流程把「复杂需求」从对话里捞出来，落成仓库里可 review、可追溯、可交接的文档，**用户点头后才动代码**。

核心原则：**文档是产物，不是仪式**。写不出来的部分说明还没想清楚，那正是要问用户的地方。

---

## 第 0 步 · 判定要不要走本流程

**走**（命中任意两条，或命中一条「强信号」）：

- 强信号：用户明说「先出设计 / 先写需求 / 出方案 / 先别动代码 / 讨论清楚再做」。
- 强信号：新增一个子系统、新模块、新的对外协议或数据格式。
- 强信号：改动持久化格式、会话存档、迁移或跨版本兼容性。
- 跨 3 个以上模块，或跨端（macOS / Android / Go 网关 / 插件页）。
- 预计改动超过 10 个文件，或要跨多轮会话才能做完。
- 有多种明显不同的实现路线，选错代价大。
- 需求本身模糊：用户描述的是**问题或愿望**，不是**要改哪里**。

**不走**（直接动手）：

- 单点 bugfix、崩溃修复、文案 / i18n / 版本号 / CHANGELOG。
- 纯重构、格式整理、测试补齐。
- 已经有设计文档在仓库里，本次只是执行其中某一步——这时**读那份文档**，按它做，必要时回写进展。
- 用户明确说「直接改」「小改动别搞文档」。

判定不清（不确定性 ≥ 30%）时，按走本流程处理，但先用一句话跟用户确认：
> 这个需求我判断得先出份设计文档（理由：……），大概 X 分钟。要是你觉得没必要，我直接开工。

---

## 第 1 步 · 调查现场，别凭空写

写文档前**必须**先摸清现状。凭想象写出来的设计文档是负资产。

调查清单（按需取用，可以派 Explore / general-purpose subagent 并行做）：

1. `docs/` 下有没有相关的既有设计文档——搜关键词，别新开一份和旧文档打架的。
2. 相关代码的现状：入口在哪、现在怎么走的、有哪些既有抽象可以复用。
3. `CHANGELOG.md` 最近几个 rc 里有没有相关改动或 Known issues。
4. 项目记忆（`MEMORY.md` 索引）里有没有踩过的坑——这个仓库不少设计陷阱只记在那里。
5. 用户给的截图、报错、日志。
6. 落盘现场：`agent-sessions/` 的 JSON、`/usr/bin/log` 的时间窗、审计日志（`judge.jsonl`、`sandbox.jsonl`、`host-calls.jsonl`）。

调查结论要落进文档的「现状」一节，**带上文件路径和行号**，让 review 的人能核对。

---

## 第 2 步 · 一次问清，别挤牙膏

把待确认的问题**合并成 6–8 个高价值问题**一次问完。能从仓库、截图、既有文档推断出来的，不要问——写成「默认假设」让用户一并确认。

优先问这些方向（挑相关的）：

- 这次的**边界**：什么算做完，什么明确不做（首版范围）。
- **用户与场景**：谁在什么情况下会用到，触发路径是什么。
- **失败与边缘**：出错怎么表现，权限不足怎么办，数据缺失怎么办。
- **兼容性**：老数据、老版本、跨端对齐怎么处理。
- **验收标准**：怎么算通过，能不能自动化验证。
- 涉及界面时：平台、信息密度、UI 体系、多语言范围。

工程选型（架构、数据库、部署、测试策略）**先给推荐方案和理由**，再让用户确认，不要把选型责任丢回去。

用户说「你看着办」时，显式列出采用的默认假设，写进文档并标注 `待确认`。

---

## 第 3 步 · 产出文档

### 放哪儿、叫什么

一律平铺在 `docs/` 下，文件名全大写下划线（`SCREAMING_SNAKE_CASE.md`），沿用仓库既有习惯：

| 后缀 / 前缀 | 用于 |
| --- | --- |
| `XXX_DESIGN.md` | 设计文档：怎么实现、数据结构、关键流程、取舍。**仓库主力文体，约 20 份** |
| `XXX_REQUIREMENTS.md` | 需求文档：对外契约式的端点、协议、验收标准。契约性弱的需求收进 `_DESIGN` 开头即可 |
| `XXX_PLAN.md` | 执行台账：编号任务、归属、依赖、验收 |
| `REVIEW_<YYYY-MM-DD>_XXX.md` | 对既有实现或某个分支的审查结论，日期在主题前，用连字符 |

日期格式在仓库里不统一，本流程**一律用连字符 `YYYY-MM-DD`**，且只有 `REVIEW_` 这类按次归档的文档才带日期。

### 出几份，看规模

| 规模 | 产出 |
| --- | --- |
| 单模块改造 | 一份 `XXX_DESIGN.md`，需求收在 `## 0. 需求来源` 里 |
| 跨模块 / 新子系统 | `XXX_REQUIREMENTS.md` + `XXX_DESIGN.md` 两份 |
| 要分阶段交付 | 再加 `XXX_PLAN.md` |

宁可少写一份，不要为凑数拆文档。

### 关于架构文档

**仓库根目录没有 `ARCHITECTURE.md`**——`BundledAgentRules/ARCHITECTURE.md` 是随 App 分发的规则库自己的架构文档，不是 Xedit 的，不要往那里写。

所以架构性结论落在设计文档的 `## 总体架构` 一节。只有当本次改动确实动了系统边界、模块划分、数据流或部署拓扑，**且用户同意新开一份**时，才在仓库根建 `ARCHITECTURE.md`，模板用 `BundledAgentRules/version-control.md` 里 `## ARCHITECTURE.md` → `### 推荐模板` 那一段，别另起炉灶。

### 怎么写

模板与章节骨架见 [templates.md](references/templates.md)。硬性要求：

- 开头一个 `>` blockquote 元信息块（**不是 YAML front-matter**），字段和取值见模板。
- 章节带阿拉伯数字编号，从 `## 0.` 起（0 号留给需求来源 / 背景与动机）。
- **现状盘点必须带代码锚点**：表格列出 `文件:行` 和它现在干什么。凭想象写的设计文档是负资产。
- 所有还没定的地方显式标 `待确认`，集中收在 `## 待确认问题` 一节，不要用含糊措辞糊过去。
- 写取舍：为什么选 A 不选 B，B 的代价是什么。看不出取舍的设计文档等于没设计。
- 写失败路径：加载中、空、错误、无权限、成功反馈、危险操作确认。
- 写验收标准和测试计划，最好是可执行的测试或命令。
- 涉及安全、审批、沙箱边界的，单列一节写清**不可让渡的不变量**，并说明拦截点在执行路径而不是 UI。

---

## 第 4 步 · 停下来，交给用户

文档写完**停住，不要顺势开工**。给用户一段简短交底：

1. 产出了哪几份文档（用可点击的相对路径）。
2. 核心方案一两句话说清楚。
3. **列出所有 `待确认` 项**，逐条问，别埋在文档里等人自己翻。
4. 明确说：确认后我就按这份文档开工。

用户回复前不要改任何生产代码。用户如果要求改文档，改完再停一次。

---

## 第 5 步 · 确认后开工，并回写文档

用户点头后：

1. 按项目 Git 规则从 `develop` 拉工作分支（见仓库根 `CLAUDE.md`）。
2. 把 `## 待确认问题` 里的条目搬进 `## 已确认决策（<拍板日期>）`，元信息块的状态改成 `已确认，实施中`。
3. 实现过程中方案有变——**回写文档**，不要让代码和文档打架。
4. 实现完成后状态改成 `已实现（<版本号>）`，并在 `### 落地后补记的实现要点` 里写实际落地与设计的差异。这份文档同时是决策台账，后面接手的人靠它还原当初为什么这么定。

## 安装备注

- 本技能是**项目级**的，只在 Xedit 仓库内生效，路径固定为 `.claude/skills/spec-first/SKILL.md`。
- 改完技能文件**当前会话不会重新加载**，要新开一个会话才认。
- 名称冲突时优先级是 Enterprise > Personal > Project，也就是说**全局 `~/.claude/skills/spec-first/` 会掩盖这一份**。以后要装全局版本，要么换个名字，要么就让全局那份取代它，别指望两份合并。
