# 第 6 章 第一个完整任务

前面五章是准备，这一章开始真干。跟着做一遍，你会把前面学的东西全用上一次。

## 6.1 先选一个合适的任务

第一个任务最好满足三条：

- **你自己能判断对错**。别拿一个你也说不清标准的活当第一个。
- **改动范围小**。改一两个文件，不是重构整个模块。
- **有现成的验证方式**。能跑测试、能打开页面看、能执行命令看输出。

几个合适的起手式：

- "读一遍这个项目，告诉我它的模块划分和数据流，写到 `docs/overview.md`。"
- "这个仓库里 `xxx` 函数在哪被调用？列出调用点和各自传的参数。"
- "把 README 里过时的安装步骤按现在的 `package.json` 更新一遍。"

不合适的：

- "把这个项目重构一下。"（没有验收标准）
- "帮我看看有什么可以优化的。"（范围无限）
- "上线到生产。"（第一次就动生产，别）

## 6.2 第一步：建会话、绑工作区

1. **⌘N** 新建会话。
2. 点输入框上方的"选择文件夹"，选你的项目目录。
3. 确认"运行位置"是"本地处理"。
4. 看一眼下面三个控件：模型选好了吗、任务模式是"普通"、审批模式是"智能审核"。

绑好之后，右边打开"文件"面板，能看到项目的文件树，说明它确实看得见你的项目。

## 6.3 第二步：把任务描述写好

这是整件事里最值钱的两分钟。一个能用的任务描述包含四块：

```
【目标】把 README 的安装步骤更新到与 package.json 一致。
【范围】只改 README.md，不要动代码。
【验收】步骤里提到的命令都能在当前依赖版本下跑通；Node 版本要求与 engines 字段一致。
【约束】保留原有的中英双语结构，不要重排章节顺序。
```

对比一下容易出事的写法："帮我更新一下 README"。它会改掉多少东西，取决于它当时怎么理解"更新"。

几个实用技巧：

- 用 `@` 引用具体文件，比在描述里写文件名更准。
- 用 `@workspace` 让它先拿到工作区的目录结构概览。
- 想让它先给方案再动手，就直接说："先给我方案，我确认后再改文件。"
- 需要它按某个既定流程做事，用 `$` 挂一个技能（[第 13 章](13-extensions.md)）。

写完按 **Return** 发送。

## 6.4 第三步：看它干活

发出去之后，对话里会依次出现这些东西：

**工具卡** —— 每次它读文件、跑命令、改文件，都会留下一张卡，写着做了什么。点开能看参数、命令、输出。这是你了解它在干嘛的主要窗口。

**计划卡** —— 多步任务会先出计划。展开看一眼，方向不对就直接改步骤或者让它重新规划（[第 7 章](07-task-modes.md)）。

**审批卡** —— 需要你点头的动作会停下来等你。看清楚它要干什么再点。四个按钮的区别见[第 8 章](08-approvals-and-sandbox.md)，第一次做任务时建议只点"允许"，别急着用"始终允许"。

**状态栏** —— 最下面显示"正在思考"之类的状态，右边的环显示上下文用了多少。

## 6.5 第四步：中途想说话怎么办

**它正在跑，你又想补一句**：直接打字发送，消息会**排队**，不会打断当前这一轮。排队的消息可以编辑、删除、调整顺序，也可以"立即发送"提到队首。

**方向明显跑偏了**：点发送按钮位置的方块停止，或者用 `/stop`。停止之后它会告诉你本轮起的进程是怎么处理的——已经停了、自己结束了，还是保留继续跑。

**它问你问题**：会出现一张卡，可能是选项按钮，也可能是输入框。回答它，或者点"跳过"。

有一点要注意：**你发新消息会结束当前尚未回答的确认和询问**，那些旧的确认会按"未授权"结算，不会再生效。所以别让审批卡和新消息抢道。

## 6.6 第五步：验收

Agent 说"完成了"不等于完成了。按这个顺序核：

1. **打开"审阅"面板看 Diff**。它到底改了哪些文件、改了什么。这一步不能省（[第 10 章](10-review-and-commit.md)）。
2. **跑验证**。让它跑测试、或者自己在终端跑一遍。看输出，不看它的转述。
3. **对照验收条件逐条打勾**。你在任务描述里写的那几条，一条条核。

发现问题就接着说，不用重开会话：

> 第 3 步的命令在 Node 18 下会报错，engines 里写的是 >=20，改成 20 并说明原因。

## 6.7 第六步：收尾

- 改动满意了，在"审阅"面板底部填提交信息，点提交；需要推送用 **⌘↩**。
- 右键会话 → "用 AI 总结标题"，给它起个能搜到的名字。
- 这个任务告一段落了，归档它。

## 6.8 新手最常踩的五个坑

1. **任务描述太短，改动范围失控**。多写三行验收条件，比事后回滚省事。
2. **不看 Diff 就信"已完成"**。模型会把测试改绿而不是把代码改对。
3. **一上来就用"完全访问"图省事**。等你熟悉了它的行为再说。
4. **一个会话里连着做三件不相干的事**。上下文越滚越贵，还容易互相污染。
5. **让它动生产环境**。第一次、第十次都别。

## 本章检查点

- [ ] 你完整跑完了一个任务：描述 → 执行 → 审批 → 验收
- [ ] 你在"审阅"面板里看过这次的 Diff
- [ ] 你至少处理过一张审批卡
- [ ] 你知道正在响应时发消息会进队列
