# 第 14 章 自动化：定时任务、调度台与专家圆桌

侧边栏上面那三个入口——已安排、调度台、专家圆桌——分别对应三种"不用你一直盯着"的工作方式。这一章逐个讲。

## 14.1 定时任务：按时自己跑

**入口**：侧边栏 →「已安排」。

**新建一个**，需要填这些：

| 字段 | 说明 |
|---|---|
| 名称 | 默认"未命名自动化"，占位示例是"如：每日 PR 摘要" |
| Prompt | 界面上写着"Prompt（每次运行作为首条用户消息）"。**必须自包含**——它开的是一个全新会话，没有上下文 |
| 工作区 | 可以不绑，也可以固定到某个本地或远端项目 |
| 模型 | 跟随当前路由，或者指定一个 |
| 调度 | 见下 |
| 启用 | 保存后是否立刻进入调度 |

**四种调度方式**：每 N 分钟 / 每 N 小时、每天 HH:MM、工作日（周一到周五）HH:MM、每周某天 HH:MM。

**其它操作**：立即运行一次（界面上明说"不影响调度计划。即使自动化被禁用也会运行一次。"）、编辑、停用、删除。删除前的确认写得很清楚：这个任务"将停止运行，其计划、提示词和设置都会被移除。此操作无法撤销。"

页面结构是"你的任务 / 建议 / 近期运行 / 已暂停"四块。**近期运行**里每条能点开对应的那次会话，会话被删掉的显示"这个对话已不可用"。记录会区分运行中、已完成、被中断和未知几种结果——App 重启时遗留的"运行中"会被结算成"已中断"，而不是伪造成成功。任务卡上还会显示"下次 ⋯"的触发时间，暂停的明确标"已暂停"，不会假装还有下次运行。

一个陷阱要记住：**归档带活跃定时任务的会话，会把那些任务停掉并移除**。界面会弹确认告诉你有几个，但很容易顺手点过去。

**Prompt 怎么写**：因为每次都是全新会话，必须写清楚上下文。

```
不行：看看今天有没有新问题
可以：检查 /Users/me/Projects/api 仓库 main 分支最近 24 小时的提交，
     跑一遍 yarn test，把失败的用例和对应提交整理成一段中文摘要。
     如果全绿，只回复"全绿"两个字。
```

最后那句很重要。定时任务每天给你一篇长报告，你三天后就不看了。

## 14.2 会话内的定时任务

除了在"已安排"里手工建，你也可以在对话里直接说：

> 每 30 分钟检查一次 CI 状态，绿了就告诉我。

Agent 会用它的定时任务工具建一个，并在对话里留下一张"定时任务"卡片。卡片上可以"打开"跳到任务。

这类任务可以带一个**完成目标**，比如"CI on main is green"。带目标的任务每次运行都会自检目标是否达成，达成了就自己把自己删掉——所以它叫"看护任务"，不会永远跑下去。

有一点要清楚：**创建定时任务不会立刻执行任何东西**，它只是排上了。

## 14.3 调度台：把一个目标拆成任务图

定时任务解决"重复"，调度台解决"大"。

**入口**：侧边栏 →「调度台」。

**流程**：

1. **定义项目** —— 描述目标结果和验收标准。可以点"让 AI 检查目标并生成验收清单"，它会告诉你这个目标能不能正常收敛，并给出建议的表述。这只是建议，不是门禁，你不采纳也能继续。
2. **绑定工作区** —— 必须绑，否则不能开始。同一个工作区已经有运行中的调度项目时会被挡住。
3. **选 Planner** —— 负责拆解目标、生成任务图的模型，一个主模型加一个备选。
4. **配 Worker 池** —— 哪些工种参与执行、允许几个并行、在哪执行（这台 Mac 还是 SSH）、用哪个执行器。
5. **跑起来** —— 节点按依赖关系推进，看板上能看到每个节点的状态。
6. **验收** —— 可以设验收关卡，按任务逐个验收，显示"N/M 个任务已通过"。

**运行中你能做的**：停止某个节点（其它节点继续跑，之后可以重启这个节点）、调整计划、追加任务、直接向项目发指令（比如"先让 Codex 跑回归测试，再请 Claude 复核"）。

调度台适合的是那种"我知道要什么，但拆起来很烦"的工作。不适合探索性的活——目标都说不清楚的时候，任务图只会把混乱结构化。

## 14.4 专家圆桌：先吵一架再动手

**入口**：侧边栏 →「专家圆桌」。

它让多个角色就同一个问题各自发言，然后收敛成一份文档。流程是这样的：正在组建专家席 → 正在框定议题 → 圆桌讨论进行中 → 正在等你的答复 → 正在收敛结论。

界面上有"态势看板"和"立场光谱"（支持 / 反对 / 中立 / 待定），能看出分歧在哪。你可以引用某位专家的整段发言或者其中一句话追问。讨论收敛之后，选"继续下一轮"或"结束并生成文档"，结论会自动存成 Markdown。

适合的场景：技术选型、方案对比、要不要做某个功能这类没有唯一答案的决定。不适合的是有确定答案的问题——那种直接问就行，开个圆桌只是烧钱。

## 14.5 内置工作流

斜杠命令里有一批多步工作流，可以当成"预制的自动化"：

| 命令 | 做什么 |
|---|---|
| `/research <问题>` | 多角度联网研究，结论会被对抗性验证 |
| `/code-review [--pr <#>]` | 从四个维度审当前 Git 改动或某个 PR |
| `/bug-hunt [范围]` | 扫工作区找可能的 bug |
| `/competitor <产品名,产品名>` | 并排比较几个产品 |
| `/pr-review <PR 号>` | 深度审一个 GitHub PR 并给结论 |
| `/release-notes <起始 tag>` | 生成从某个 tag 到 HEAD 的发布说明 |
| `/issue-triage [标签]` | 给未关闭的 issue 分类排优先级 |
| `/csv-ask <文件> <问题>` | 用 DuckDB 查本地 CSV/Parquet 并解释结果 |
| `/db-explore <连接串> <问题>` | 用自然语言查数据库（**只读**） |
| `/db-schema-doc <连接串>` | 把数据库反向工程成 Markdown 文档加 ER 图 |

GitHub 那几条跑之前会检查 `gh` 装没装、登录没登录。数据库那几条强制只读。

## 14.6 跑完了怎么通知你

「设置 → AI Agents → 通知」：

- **后台通知声音** —— 无 / 系统默认 / 自定义音频（MP3、AIFF、WAV、CAF、M4A，不超过 30 秒）。在后台等你授权、确认或回答时会响。
- **Webhook** —— 填一个地址，订阅两类事件：外部执行器任务完成、需要授权确认或回答。可以发测试。

Webhook 的隐私边界写得很明确：**只发事件元数据、会话标题、执行器、状态和时间，不发命令、模型输出和你的回答**。想把通知接到自己的机器人上，这个边界你得知道。

## 14.7 一套实际在用的自动化组合

```
每个工作日 09:30  → 拉昨天的提交和 CI 状态，全绿只回两个字
每 30 分钟        → 看护型任务：盯着某个部署，成功就自删
每周五 17:00      → 汇总本周改动，生成周报草稿到 docs/weekly/
需要时手动        → /code-review 在提 PR 之前跑一遍
```

## 本章检查点

- [ ] 你建过一个定时任务，并且它真的按时跑了一次
- [ ] 你的定时任务 Prompt 是自包含的
- [ ] 你知道归档会话会停掉它的定时任务
- [ ] 你至少跑过一个内置工作流
