# 第 11 章 多 Agent 协作

一个人干活有上限，一个 Agent 也是。调查、实现、验证、审查这几件事可以并行，也应该由不同的角色来做——让写代码的那个自己审自己，结果你能猜到。

这一章讲怎么把活分出去。

## 11.1 六个公开工种

在输入框里打 `@`，排在最前面的就是可以点名的 Worker：

| 点名 | 中文名 | 干什么 | 能写文件吗 |
|---|---|---|---|
| `@scout` | 调查 | 找文件、找符号、找调用点。最快最省 | 不能 |
| `@generalist` | 通用 | 没有更合适工种时的兜底，能改已声明的文件、用终端、用已配的 MCP | 能（限已声明路径） |
| `@implementer` | 实现 | 在最多 16 个已声明路径里做有界的多文件改动 | 能 |
| `@tester` | 验证 | 跑测试和门禁、产出证据 | **从不改代码** |
| `@reviewer` | 审查 | 只读地复核改动范围、版本一致性、git 完整性 | 不能 |
| `@ops_runner` | 运维 | 运维查询直接执行，有限的修改命令要过审批 | 受限 |

点名时注意 `ops_runner` 是下划线，写成中划线在面板里筛不出来。

点名之后输入框上方会出现一个"派给 xxx"的 chip。**只有一个槽位**，再点一个就换人，发送时消费掉。

内部还有十几个更细的工种（阅读、深查、编辑、轻量实现、测试修复、构建修复、日志巡检、Git 溯源等），由 Agent 自己按需要选，你不用记。

## 11.2 三种派单方式

**① 点名**：`@scout 找出登录失败时的错误码是在哪里生成的`

**② 强制委派**：`/subagent <要子代理调查什么>`
这一轮强制走委派，不让主 Agent 自己干。

**③ 禁止委派**：`/no-subagent <要主代理独立完成什么>`
这一轮直接把派子 Agent 的能力从工具表里摘掉，硬保证它自己动手。

后两条可以写在句尾：`把这批测试跑一遍 /no-subagent`。

还有一个常驻设置：输入框"更多设置"里的**执行优先级**，两个选项——"子 Agent 优先"（默认）和"Agent 优先"。前者鼓励它拆活出去，后者让它自己上。这个设置随会话保存。

## 11.3 前台还是后台

派出去的 Worker 有两种跑法：

- **前台**：主会话等它，结果回来再继续。
- **后台**：主会话继续和你对话，Worker 在后台跑。

后台有硬门槛：**这个子任务必须真的独立**，而且必须说明主会话同时在干什么。另外，**要写文件的 Worker 必须前台跑**——避免你在前面聊天、它在后面悄悄改文件。

后台 Worker 的进度会显示在输入框上方的状态条里，而且它独立于主会话的生命周期：主会话这一轮回复结束了，状态条还在，直到所有 Worker 都结束才消失。

## 11.4 看它在干什么

**Worker 监控行**：显示"子代理运行中"、当前阶段（定位 / 读取 / 实现 / 验证）、运行时长、工具调用次数。

**运行详情（检视器）**：点开能看到分工、提示词、推理过程、参数、每一轮的动作、最终报告，底部有"N 轮 · M 次工具调用 · X tokens"的统计。Worker 的结论可疑时，来这里看它到底看了什么、跑了什么。

**舰队面板**："N 个 Worker 正在运行"，点进去是全部运行中的 Worker。

**后台任务面板**：Worker 起的进程都在这里，能按会话筛、搜索、看 PID 和命令、复制输出、单独停掉。

## 11.5 中途纠正：干预

发现 Worker 走歪了，不用等它跑完。检视器里有"干预子代理"，输入框提示是"纠正子代理的下一步…"。

两种投递方式：

- **下轮生效**（普通发送）：当前这一步做完之后生效。适合微调方向。
- **打断并发送**：立刻终止当前步骤并注入你的指令。适合它正在往错误的方向猛跑。

按 **⌘↩** 是下轮生效发送，回车是换行。

## 11.6 停止与结算

后台 Worker 列表支持逐个停止，停一个不影响其它的。停掉之后**不会自动唤醒主会话继续跑**，需要你自己接着说。

停止之后的结算信息要读一下，它会明确告诉你进程是怎么处理的：

- "N 个本机进程已退出。"
- "未向 N 个独立进程发送停止信号。"
- "已请求取消 N 个托管任务；尚未确认远端进程退出。"

最后一种尤其重要：**远端进程可能还在跑**，别急着重启一遍同样的任务。

## 11.7 上下文档位

派 Worker 时可以选能力档：**基础 / 进阶 / 专家**，对应不同的模型。上下文预算有 64K / 128K / 256K / 1M 四挡，默认 256K。

有一条常见的误解要澄清：**上下文预算是上限，不是对模型能力的声明**。你把它设成 1M，模型本身吃不下的话，只会在 provider 那边报溢出错误。派发时系统会 clamp 到模型实际窗口，但设得离谱仍然会出问题。

同样，能力档只影响用哪个模型，**永远不会扩大工具集、写入范围或命令审批的边界**。

## 11.8 自动派发：测试修复和构建修复

有一类派发不需要你和主 Agent 参与：验证命令跑失败时，系统会直接派出"测试修复"或"构建修复"工种去处理。

触发条件很严：只有当失败日志里能解析出明确的可写文件集合时才派，写集上限 8 个文件，每条命令每轮只派一次。派不出去的时候会把原因写进工具结果里，不会静默跳过。

## 11.9 什么时候值得分工

| 场景 | 建议 |
|---|---|
| 找一个东西在哪 | `@scout`，最省 |
| 大改动前先摸清现状 | `@scout` 调查 → 主 Agent 实现 |
| 改完要验证 | `@tester` 跑测试，它不会顺手改代码 |
| 改完要复核 | `@reviewer`，独立视角 |
| 几件互不相干的事 | 后台派出去并行 |
| 一件事拆成的连续步骤 | **别拆**。互相依赖的步骤并行只会互相等 |

一条经验：**分工的收益来自并行和隔离，不来自"人多力量大"**。一个简单任务派三个 Worker，只会得到三份互相矛盾的报告。

## 11.10 代理档案设置

「设置 → 代理档案」能调每个工种的细节：

- **模型**：每个工种用哪个服务商、哪个模型。留空表示跟随上级会话。
- **职责**：一行职能描述，加上专属提示词。内置工种的几条不变量（只读边界、"最后一条消息就是交付物"、"不能问用户"）不在这里改。
- **工具权限**：内置工种的工具集是固定的——正是这份窄工具集让它又快又准。要自定义工具集就新建一个档案。
- **最大上下文 / 最大轮数**：预算。

登录 some.im 时，托管的那几个工种会锁定模型和提示词，界面会写明"模型与提示词由 some.im 托管"。
