# 内置浏览器授权减负

> 状态：1.399.0-rc1 起分步实施 · 取代 1.396.0-rc3 的“按工具授权”

## 背景

1.396.0-rc3 把浏览器的“一直允许”从整族（`browser:embedded`）收窄到单个工具，并让
`embedded_browser_eval` 每次都单独确认。结果是：一次普通的浏览任务里，打开网页、
点击、输入、执行脚本各要批一次，eval 每调用一次就问一次。实测百度任务“杭州一日游的
第一个非广告结果”连问了 4 次，而模型写的 4 段脚本都只是在读 DOM。

目标：**只在有后果的时刻问**，而不是按工具问。

## 前提：登录态的风险边界

内置浏览器的脚本运行在页面上下文里，读不到 httpOnly cookie；敏感登录态都在 httpOnly
cookie 里。读到非 httpOnly 的 cookie 或 localStorage 可以接受（产品决定，2026-09-22）。
所以**不对工具结果做按值脱敏**。

真正要防的是两件事：以用户的身份做了不可撤回的动作；把本地数据或登录态送出去。

## 第 1 步：声明式提取（1.400.0-rc1）

`embedded_browser_extract(selector, fields, limit, max_chars)`：对每个匹配的元素取出字段
（文字 / 属性 / exists / count），只读，不需要审批。它替代了大部分“写脚本探页面结构”
的 eval。

## 第 2 步：只读脚本免确认（1.401.0-rc1）

`AgentBrowserScriptClassifier` 是确定性的黑名单：脚本里没有发请求、跳转、提交 / 点击 /
派发事件、改 DOM、写存储、动态执行或混淆写法（`eval`、`Function`、`atob`、
`window['fe'+'tch']`、`\u` 转义、`constructor` 等），就判为只读，在没授权的网站上也
直接放行（来源记为 `staticAllowlist`）。

- 放在 Strict（每次都问）之后：选了严格模式仍然询问。
- 带密钥占位符 `${secret:` 的脚本不免确认：页面可以劫持 DOM 函数看到解析后的值。
- 规则编译失败、脚本为空或超过 20000 字符：一律判为非只读（fail-closed）。
- 判不准的脚本回到第 3 步的网站授权，不会因为分类器漏判而放宽。

## 第 3 步：按网站授权 + 有后果的动作单独确认

### 3a 网站授权（1.399.0-rc1）

1. **eval 不再逐次确认**，与其他内置浏览器工具同等对待。
2. **仍逐次确认的只剩两个**：`chrome_debugger_command`（CDP 能读出包括 httpOnly 在内
   的全部 cookie）和 `embedded_browser_upload_file`（把本地文件发给网站）。
3. **“一直允许”按网站生效；“本会话允许”仍是整个内置浏览器**（只在当前会话有效、由用户
   明确点选）。网站规则的签名形如 `browser:embedded:site:www.baidu.com`：
   - navigate 用目标地址的域名；
   - 其余内置浏览器工具用**发起调用时**页面所在的域名。宿主在调用登记时把域名写进隐藏
     参数 `_willdeep_page_host`，模型传入的同名参数会被覆盖；
   - **执行时复核**：页面在批准后跳到了别的域名，调用直接失败并要求模型重新发起；
   - 空白页和本地文件没有域名，不产生网站授权，照常询问。
4. Chrome（`chrome_*`）暂不改：宿主拿不到 Chrome 当前标签页的同步地址，仍按单个工具授权。
5. 1.396.0-rc3 到 1.398 存下的按工具规则继续匹配；新批准一律存成网站规则。

### 3b 有后果的点击单独确认（1.402.0-rc1）

在已授权的网站上，点击（以及对按钮 / 链接按 Enter、空格）如果目标元素的文字看起来会
**发送、提交、发布、删除、购买 / 付款、转账、授权、同意条款、改账户、登录**，仍然弹卡：

- 宿主在登记调用时读出目标元素的可见文字（innerText / value / aria-label / title，
  最多 80 字符），写进隐藏参数 `_willdeep_target_label`；
- 用与 Computer Use 相同的关键词分组（`AgentComputerUseConsequence`）判定；
- 命中时网站规则和“本会话允许”都不生效，卡片说明原因；完全访问和 Goal 模式不变；
- 读不到元素文字时按普通点击处理：网站规则本来就只覆盖用户已允许的网站。

## 第 4 步：独立浏览器（不带登录态）（1.403.0-rc1）

内置浏览器提供两套数据存储：

- **我的浏览器**（默认，行为与以前一致）：`WKWebsiteDataStore.default()`，带用户登录态和
  从 Chrome 导入的 cookie；
- **独立浏览器**：`WKWebsiteDataStore(forIdentifier:)` 固定一个标识，持久但与“我的浏览器”
  完全隔离，没有用户的登录态。

在独立浏览器里，内置浏览器的普通操作（打开、点击、输入、按键、滚动、执行脚本）**不需要
确认**：没有登录态，就没有“以用户身份”可言。上传和第 3b 步的有后果动作仍然确认。

- 切换入口在内置浏览器面板的工具栏；同一会话的新标签页沿用最后一次选择，会话释放后恢复
  默认“我的浏览器”（不跨重启持久化）；
- 独立浏览器里禁用“从 Chrome 导入登录”；
- 带密钥占位符 `${secret:` 的调用在独立浏览器里也要确认（把保存的密钥输入网站）；
- 宿主写入 `_willdeep_browser_profile`，批准后切换过配置的调用在执行前拒绝；
- `embedded_browser_status` 返回当前是哪一套，模型能知道自己在哪；
- 切换时重建 WebView，当前页面按新存储重新加载。

## 不做的事

- 不做工具结果的按值脱敏（见“前提”）。
- 不给 Chrome 做网站授权。
