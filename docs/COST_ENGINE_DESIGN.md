# WillDeep 成本引擎设计：客户端与服务端协同花钱

> 状态：提案
> 日期：2026-08-09
> 关联：[CROSS_PLATFORM_CLI_STRATEGY.md](CROSS_PLATFORM_CLI_STRATEGY.md) 第 7.5 节
> 北极星指标：**每个验收通过任务的总成本**（含失败重试与升档开销），不是每 token 单价。用错度量，越省越亏——最贵的 token 永远是失败任务的 token。

## 1. 分工总原则

一句话：**谁离信息近，谁做决策；花钱动作发生在哪，就在哪设闸**。

| 职责 | 归属 | 理由 |
|---|---|---|
| 上下文卫生（折叠、裁剪、窄化） | 客户端 | 源码和会话在本地，隐私 + 就近 |
| 任务特征提取 | 客户端 | 只上报结构化元数据，不上报源码 |
| 模型选择与升降档决策 | 服务端（托管）/ 本地规则表（BYOK） | 服务端握有实时价格、配额、跨用户成功率 |
| 预算执行与硬顶 | 客户端 | 请求发出前拦截，不事后追悔 |
| 缓存亲和与会话调度 | 服务端 | 需要跨请求视野 |
| 错峰与批处理调度 | 服务端 | 掌握价格日历与队列 |
| 遥测聚合与路由表更新 | 服务端 | 飞轮所在 |
| 收据生成 | 服务端出账、客户端展示（BYOK 本地估算） | 计费真相在服务端 |

一条铁律：**服务端只见元数据，不见源码**。路由所需的一切特征由客户端提取为结构化字段。

## 2. 六大机制

### 2.1 分层路由与升降档

任务由客户端 orchestrator 分类并提取特征，服务端（或 BYOK 本地规则表）返回路由决策：

```text
客户端上报（元数据）                服务端返回
┌─────────────────────┐          ┌─────────────────────┐
│ task_class: implement│          │ model: deepseek-v4   │
│ est_ctx_tokens: 18k  │  ──────▶ │ budget: ¥0.80        │
│ lang: swift          │          │ escalation: 2-fail   │
│ prior_failures: 1    │  ◀────── │ cache_hint: sess-aff │
│ interactive: true    │          │ fallback: <premium>  │
└─────────────────────┘          └─────────────────────┘
```

- **任务分类**：`search` / `summarize` / `classify` / `mechanical-edit` / `implement` / `plan` / `review` / `test-fix` / `judge`。
- **升档阶梯示例**：deepseek-v4-flash → deepseek-v4 → 高档模型（Claude / GPT / Gemini，按可用性与任务类别）。
- **升档触发只有三条，写死**：
  1. Planner 判定任务复杂度超阈值；
  2. 验证失败 N 次（默认 N=2）；
  3. 用户显式指定。
- **辅助升档信号**（计入第 2 条的失败计数）：tool-call 解析连续失败、diff 应用失败、输出被截断。
- **MUST NOT 静默降档**。所有升降档事件写入任务收据。
- 路由裁判自身用 flash 档（沿用 someim-judge 先例），但 **max_tokens 必须给足**——历史教训：智能审批裁判曾因 max_tokens:16 在 reasoning 模型下全程静默必败。裁判请求失败必须显式降级到规则表，不允许静默放行或静默阻塞。

### 2.2 Prompt Cache 协同（最大杠杆，命中省约 90%）

**客户端：稳定前缀纪律**

- system prompt、工具定义、`AGENTS.md` 按固定顺序拼装，会话正文 append-only；
- **禁止**在前缀区注入时间戳、随机数、动态统计等易变内容；
- 上下文折叠时保持已缓存前缀段完整，折叠只发生在前缀边界之后；
- 折叠导致前缀失效 = 一次静默的十倍涨价，折叠时机要与缓存生命周期权衡。

**服务端：缓存亲和调度**

- 同一会话的连续回合路由到同一 provider/endpoint，保住缓存命中；
- 按 provider 特性配置：Anthropic 显式 `cache_control` 断点、DeepSeek 自动上下文缓存等；
- 缓存命中率进遥测和收据；会话中途换模型（升档）前先评估缓存损失是否被升档收益覆盖。

### 2.3 上下文纪律（客户端，多 agent 省钱的唯一来源）

天真的多 agent 是费钱的：协调开销 + 重复上下文，token 总量不降反升。省钱的真实来源：

- **子 agent 窄上下文**：orchestrator 只下发任务简报 + 相关文件清单，不转发全量会话；机械子任务（搜索、摘要、跑测试并解读）用短窗口便宜模型；
- **辅助请求走主折叠管线**：压缩/摘要类请求必须与主请求走同一条上下文折叠管线并分块（Swift 侧血泪教训，直接立法）；
- **repo map 本地缓存**：增量更新，不每回合重建；
- **工具输出裁剪**：测试日志取失败聚焦段 + tail；超长输出先由 flash 摘要，再进主模型上下文。

### 2.4 预算包络与硬顶（客户端执行）

- 每个任务携带预算包络：托管模式由服务端随路由决策签发，BYOK 本地配置默认值；
- 执行规则：**70% 预警 → 100% 需审批才能继续 → 绝对硬顶杀任务**；
- 预算超限是标准审批事件，走现有审批链推送到手机——"要不要多花钱"本来就该在手机上按；
- `goal` 分解时把总预算切分给子任务，Integrator 汇总实耗；
- **后台任务 MUST 有硬顶**，无人值守的 runaway agent 一夜烧钱是本设计的头号防御对象。

### 2.5 错峰与批处理（服务端调度）

- 客户端为任务标注时效性：`interactive`（立即）/ `background`（尽快）/ `schedulable`（窗口内完成即可）；
- `schedulable` 的后台 goal 由服务端排到低谷时段（如 DeepSeek 低谷折扣时段）或 batch API；
- **"明早 8 点前完成"比"现在就做"便宜得多**——这本身可以做成定价差异和产品卖点，与"离开终端任务继续跑"的产品叙事天然互相成就。

### 2.6 小活不进云

**定义**：Agent 会话中高频、低价值、质量地板低的微型调用。若内联在主模型对话里做，付的是"贵模型单价 × 全量上下文"的钱，干的是几百 token 的活，还砸掉主对话缓存前缀——双重浪费。一个 50 回合会话约产生几十次此类调用，内联单次 ¥0.1–0.5，旁路到 flash/本地模型后单次 <¥0.001，合计可占任务总成本的 10–20%，而质量损失约等于零。

**小活清单与去处**（每行必须有非模型兜底——这是"some.im 非必要条件"与离线可用的保障）：

| 小活 | 首选去处 | 兜底 |
|---|---|---|
| commit message / PR 描述 | 本地小模型 | flash → 模板拼接 |
| 会话/任务标题 | 本地小模型 | flash → 截断首句 |
| 任务分类打标（路由特征提取） | 本地小模型 | flash → 规则表 |
| 长工具输出摘要（测试日志、build 输出） | flash | 截断取 tail + 失败聚焦段 |
| 错误归类（flaky / 环境 / 真代码错） | flash | 不归类，原样上报 |
| diff 摘要（收据与验收报告用） | flash | 按文件名统计行数 |
| 敏感信息粗筛（日志脱敏预检） | 本地小模型 | 正则规则 |

**三条设计规则**：

1. **不进主上下文**：小活一律是独立旁路请求（side-call），绝不出现在主对话里——既省钱，也保住 2.2 的缓存前缀稳定。
2. **正确性边界**：小活的定义是"输出不承载正确性"，flash 永远不直接决定代码怎么改。灰色地带显式处理：测试日志摘要会喂回主模型影响判断，故摘要 MUST 保留原始失败断言的原文引用（不许转述），且主模型可索要原文。一旦某类小活的输出开始影响决策质量，它就不再是小活，进 2.1 升降档体系管理。
3. **单独记账**：小活开销计入收据的 overhead 行，不占任务预算包络主额度——否则预算临界时系统会"舍不得"写 commit message，行为怪异化；单列一行也让用户看见"这部分被省到接近零"。

**本地模型探测阶梯**（CLI 不内置模型权重，只做探测与适配，启动时按序探测）：

1. macOS：Apple 端侧基础模型 API（系统自带，零成本零延迟，隐私最优）；
2. 跨平台：探测本机 Ollama / llama.cpp 及可用小模型（Qwen3-4B 级别即够用）；
3. 都没有：落到 flash 档（some.im 或 BYOK）；
4. 无网络：非模型兜底（模板 / 规则 / 截断）。

探测结果进 `willdeep doctor` 诊断输出，用户可见"小活当前跑在哪一档"。

**与飞轮的关系**：服务端维护"任务类别 → 最低可用档位"映射表，遥测数据（如"标题生成用 4B 模型与 flash 的用户采纳率无差异"）驱动该表持续下修或上调——省钱能力随数据变强，是托管版的又一增值点。

## 3. 账本与数据飞轮

账本（Ledger）是成本引擎的一等公民：收据、省钱报表、遥测、飞轮分析都是它的派生视图。没有账本，所有经济优化都是拍脑袋。

```text
LedgerEntry（账本：最细粒度事实，每次 LLM 请求一条）
   ├─▶ Receipt        （按任务聚合 → 给用户看的收据）
   ├─▶ 月度省钱报表    （按时间聚合 → 传播物料）
   ├─▶ TelemetryEvent （脱敏子集上报 → 喂飞轮）
   └─▶ 分析查询        （按任意维度切 → 经济优化）
```

### 3.1 LedgerEntry：每次 LLM 请求落一条

```text
timestamp · session_id · task_id · goal_id
agent_role(planner/implementer/tester/reviewer/judge/小活)
task_class · model · provider
tokens_in / tokens_out · cache_read / cache_write（分开记）
cost_billed（实付价）· cost_list（牌价）
latency · escalation_flag · outcome（关联任务验收结果）
```

### 3.2 四条会计原则（缺一条分析就瘸）

1. **权责发生制**：成本记在产生它的任务头上，不是月底一锅粥——否则北极星"每验收任务总成本"根本算不出来；
2. **双价记账**：实付价与牌价都记，差额 = 缓存折扣 + 错峰折扣 + 路由降档节省——**"省了多少钱"只有双价才算得出来**，省钱报表的数字全靠它；
3. **失败也记账**：失败重试、升档重来的开销全部归属原任务——便宜模型到底划不划算，答案藏在这里；
4. **overhead 单列**：小活开销独立科目（落实 2.6 规则 3）。

### 3.3 存储与归属

- 本地 SQLite：一张事实表 + 若干聚合视图，足够，不上重型数仓；
- BYOK 用户：完整账本在本地，隐私自持；
- 托管用户：服务端账单为权威，本地留镜像，两边可对账。

### 3.4 分析层：`willdeep cost`

```bash
willdeep cost                     # 本月概览：总支出、节省额、北极星走势
willdeep cost --task <id>         # 单任务成本剖面
willdeep cost --by model|role|class|hour
willdeep cost --export csv
```

分析问题与优化动作一一对应，构成经济优化工作流（看账本 → 找异常科目 → 调参 → 下期账本验证）：

| 分析问题 | 驱动的优化 |
|---|---|
| 升档率多高？升档后成功率提升多少？ | 升档阈值 N 调松或调紧（升档不值 = 白花钱） |
| 缓存命中率随会话长度怎么衰减？ | 折叠时机与前缀策略调参 |
| 失败重试占总成本几成？ | 哪些任务类别应直接从高档起步 |
| 哪个 agent 角色是成本大头？ | 窄化该角色上下文、或降档 |
| flash 在哪些任务类别验收率已追平高档？ | 路由表下修，扩大便宜模型适用面 |
| 每小时成本分布？ | 错峰调度窗口选址 |

### 3.5 飞轮回路

遥测事件是账本的**脱敏子集**（去掉本地 ID 细节，保留统计维度），上报后进飞轮：

```text
账本（本地事实）→ 脱敏遥测 → 服务端聚合 → 路由表更新 → 下发客户端
     ↑                                              │
     └───────────────── 路由越用越准 ◀───────────────┘
```

- **可验证交付提供训练标签**：测试通过/失败、用户采纳/改写，就是"这个档位够不够"的真实答案。这是纯 API 转售商和单一模型厂都拿不到的数据。
- **冷启动**：手写路由规则表 v0 随 CLI 发布，飞轮数据逐步替换人工规则。

### 3.6 隐私红线

- 账本本身留在本地；上报的遥测**不含**源码、文件路径、prompt 正文；
- BYOK 用户遥测 **opt-in**；托管用户默认开启、可关闭；
- 聚合统计匿名化，单用户数据不对外。

## 4. BYOK 与托管的能力差异（商业化钩子）

| 能力 | BYOK | some.im 托管 |
|---|---|---|
| 静态路由规则表（随 CLI 更新） | ✅ | ✅ |
| 实时价格 / 配额感知路由 | ❌ | ✅ |
| 缓存亲和调度 | 部分（单 provider 内） | ✅ |
| 错峰 / batch 折扣 | ❌ | ✅ |
| 飞轮驱动的路由持续优化 | ❌ | ✅ |
| 收据与省钱报表 | 本地估算 | 账单级精确 |

这张表就是"卖平面不卖算力"的实体：**托管比 BYOK 更省钱是产品目标**——用调度和飞轮赚出来的差价，比转售差价体面得多，也是 BYOK 用户升级托管的自然理由（不靠锁定，靠真便宜）。

## 5. 协议影响

- `protocol` crate 新增 schema（全部版本化）：`LedgerEntry`（最细粒度事实）、`RouteRequest` / `RouteDecision`、`BudgetEnvelope`；`Receipt` 与 `TelemetryEvent` 定义为 LedgerEntry 的派生视图，不独立演化；
- 审批链新增事件类型：`budget_exceeded`；
- 收据与验收报告共用一个交付结构——"账单和测试报告是同一张纸"。

## 6. 分阶段落地

| 阶段 | 交付 |
|---|---|
| 阶段 1（与 CLI MVP 同步） | 本地账本（SQLite）+ 遥测埋点、`willdeep cost` 基础版、任务收据 v0（本地估算）、静态路由表 v0、prompt cache 前缀纪律、任务级预算硬顶 |
| 阶段 2 | 服务端路由器 v1（规则 + 实时价格）、升降档阶梯、缓存亲和调度、后台错峰 / batch、双价记账与完整分析维度、账单级收据（本地/服务端可对账） |
| 阶段 3 | 数据驱动路由（飞轮闭环）、goal 级预算切分优化、企业成本策略、月度省钱报表自动生成 |

遥测埋点必须在阶段 1 落地——**飞轮数据从第一天开始攒**，路由器可以晚到，数据不能晚到。

## 7. 反模式红线

- **MUST NOT** 静默降档——用户发现被便宜模型糊弄的那一刻，信任归零；
- **MUST NOT** 后台任务无预算硬顶；
- **MUST NOT** 为省钱削减验证步骤——砍测试等于毁掉北极星指标的分母；
- **MUST NOT** 在缓存前缀区注入易变内容；
- **MUST NOT** 无窄化纪律的天真多 agent 并行；
- **MUST NOT** 裁判/路由请求配小 max_tokens（历史上必败且静默）；
- **MUST NOT** 遥测夹带源码或 prompt 正文。
