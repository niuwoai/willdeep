## 1. 用户需要的体验

共同流程：

```text
选中当前对象
    → 与 AI 对话
    → 生成结构化草稿
    → 看预览、讨论修改、手动修改
    → 用户定稿
    → 随时再次打开并继续修改
```

明确要求：

- AI 辅助生成贯穿全部文本和结构化资料阶段；只加空表单或展示页不算数。
- 每个阶段有自己的聊天区，共享整部剧的正式资料；切换阶段后聊天和草稿不丢。
- 角色、分集、分镜等对象有清楚的选中状态，用户知道正在改谁。
- 查看正文时可以选中局部，让 AI 只改这一段或这一个字段。
- AI 与手动编辑交替使用，后续 AI 请求能看到最新手改内容。
- 定稿是明确采用；聊天记录和未定稿草稿也要自动保存。
- 灰度视觉，不依赖系统蓝色强调色。

## 2. 定下来的技术路线

**首版复用现有 `ai.complete`，做固定步骤的共创流程，不做工具循环。**

插件决定当前对象和要读的资料，调用一次模型，再验证和展示结果。用户每次继续发言，执行下一轮。

```text
插件确定对象、读取当前草稿与必要上游资料
    → 构造阶段指令、用户要求和输出约束
    → 宿主 ai.complete
    → 解析与校验结果
    → 写入草稿，显示正文和差异
    → 用户继续修改或定稿
```

模型可以正常交流、解释或提问，不要求每句回复都产出完整对象；产出资料时必须是可验证的结构化结果。插件负责读取、校验、保存和定稿，模型不自主决定调用哪些读写工具。

这条路线不是"先简后繁"的权宜。当前插件 AI 通道调模型时 `tools` 走的是默认空数组，只消费文本增量，工具循环在宿主层不通。要上 harness 得先改宿主，届时优先评估复用宿主已有的 Agent 运行时，而不是给插件另建一套运行层。

判断标准是出现固定流程覆盖不了的真实用例，例如：AI 自主找出全剧矛盾并决定读哪些集数和镜头、单次任务需要反复查资料再自检、多种创作工具有真实的条件分支。名称不是目标。

## 3. 评审推翻的两条旧判断

写实现前必须知道这两件事，旧方案在这里判断错了。

**输出预算 4096 不成立，因为这个字段没生效。** 插件传的 `maxOutputTokens` 在 `Xedit/AgentPluginAIBridge.swift:207-212` 被解析并夹进 `[16, 4096]`，之后再无消费点；`runPluginAICompletion` 调 `streamChat(messages:)` 不带它，底层签名里也没有这个形参。真实上限来自 provider adapter 的全局设置。结论是长文本输出不受 4096 限制，但这是个骗人的参数，宿主文档还在教插件作者用它。

**取消不是待核实项，是确定不存在，且比设想的严重。** 没有 Task 句柄、没有流标识到请求的映射、没有取消命令，页面拆卸只移除消息处理器。关掉插件页请求会变成孤儿继续跑完、继续计费。

## 4. 真实存在的约束

宿主侧：

- 输入上限 24 条消息、合计 32,000 字符，**system 消息也计入这 32,000 字**。撞上是直接抛错不是截断。
- 技能正文另算预算，最多 3 个、每个 8,000 字，由宿主读盘注入。
- 插件 AI 通道**没有任何并发上限**（源文件头注释声称有，实为未实现）。页面可以并行发任意多次请求。
- 没有流结束和流错误事件，页面只能靠 promise resolve 判断结束。
- 插件键值存储单值 64KB、单插件合计 1MB。聊天记录放不下，必须进 Ruby 侧。
- 新增桥接命令要同时改三处契约：`Xedit/AgentPluginPageBridgeVersion.swift` 的能力清单、`BundledSkills/willdeep-plugin-dev/references/page-api.md`、插件 `plugin.json` 的 `minimumWillDeepVersion`（现为 `1.321.0-rc1`）。少一处就是旧宿主装新插件时调一个不存在的命令。

插件后端：

- 所有短剧装在一个 `dramas.json` 里，`MAX_DRAMAS = 100` 超出静默截断，每次保存全量重写整个文件。
- 每部剧内没有任何修订号，跨调用是后写覆盖，无乐观锁。唯一幂等机制是 `confirm_plan` 的请求去重。
- 后端 `save_*` 是局部合并、遇空跳过，这一点天然保护手改，直接复用。
- MCP 服务端钉死跑在 `/usr/bin/ruby` 2.6 上（`drama_service.rb:263-264`），`filter_map` 之类的新 API 不能用。R 阶段全部受这条管。

- 现有 `askPlanner` 靠 ```` ```short_drama_plan ```` 围栏从模型文字里切 JSON，流式显示时是把原文尾部直接刷在聊天区。

## 5. 数据设计

### 两个修订号，一个草稿字段

不建独立的草稿存储层。给 Drama 顶层、character、episode、shot 四种对象各加三样东西：

- `rev`：正式内容的修订号，只在定稿（commit）时自增。
- `draftRev`：草稿修订号，每次写草稿自增。
- `draft`：与正式内容同结构的对象，可为 null。

为什么要两个数：AI 请求发出后用户手改草稿，回来时要能看出"草稿变了"，靠的是 `draftRev`；而多窗口同改一部剧、或旧结果覆盖新定稿，要拦的是正式内容，靠的是 `rev`。合成一个数，要么每次手改都把在跑的请求判成冲突，要么手改保护失效。

Drama 顶层指 title、logline、arc 这些策划字段，策划阶段迁入同一套机制时用得上。

### 写路径只有两条

- **文本字段一律走草稿。** 表单手改和 AI 结果都写 `draft`，通过 `drama.saveDraft` 提交，携带 `expectedDraftRev`。
- **定稿走 `drama.commitDraft`**，携带 `expectedRev`：把 `draft` 合并进正式内容，清空 `draft`，`rev` 自增。
- 现有 `save_character` / `save_episode` / `save_shot` 这三条直写正式内容的路径**不再由前端用于文本字段**，只留给图片候选记录、选图这类非文本操作，并且同样接 `expectedRev`，避免绕过检查。

版本检查在 Ruby 侧的 `flock` 锁内做，不匹配返回明确的冲突错误码，不静默覆盖。

### AI 结果回来时怎么办

请求发出时记下 `draftRev`。结果回来：

- `draftRev` 未变：直接写入草稿。
- `draftRev` 已变（用户中途手改过）：结果**只留在内存**作为候选，提示复核，用户决定采用或丢弃。关窗即丢，首版接受。
- 对象已切换：结果按请求记录的对象 ID 归位，不写到当前选中的对象上。

### 重复确认

`commitDraft` 带 `expectedRev`，第二次点确认时 `rev` 已经变了，后端返回冲突，前端把它当成"已经定稿过了"处理，不报错不重建。幂等靠这个，不另加请求 ID。

### 聊天记录

进 Ruby 侧，**每部剧一个文件**（如 `chats/<dramaID>.json`），不塞进 `dramas.json`，也不是所有剧共用一个文件。理由都一样：全量重写的文件，每发一条消息重写整库。聊天范围键是「阶段」，消息体带对象 ID 和发出时的 `draftRev`。

### 旧数据迁移

缺 `rev` 视为 0，缺 `draftRev` 视为 0，缺 `draft` 视为 null。保留原文件与现有 ID，不默认为已定稿。

### 局部修改：完整对象加白名单裁剪

模型返回当前对象的完整候选，应用只把 `fieldScope` 白名单内的字段合并进草稿，白名单外一律丢弃。用户没指定局部时，`fieldScope` 就是全字段。

这样既不用写 JSON Patch 执行器，也不靠提示词保证其他字段不变，差异还天然可算。差异由前端计算，不采信模型自述"我只改了某处"。

## 6. 输出协议

沿用现有围栏做法，每个阶段一个围栏名：`short_drama_plan`（已有）、`short_drama_character`、`short_drama_episode`、`short_drama_shot`、`short_drama_frame`。

- 回复里**没有围栏**：当成闲聊或提问，只进聊天记录，不动草稿。
- 回复里**有围栏**：围栏外的文字进聊天记录作为说明，围栏内的 JSON 解析后按 `fieldScope` 裁剪写草稿。一条回复最多认第一个围栏。
- 围栏内 JSON 解析失败：聊天区显示原文并标记"格式错误"，草稿不动，用户可以让模型重发。首版不做自动格式修复。
- 流式显示：围栏出现之前的文字正常流式刷出；检测到围栏开头后，聊天区显示"正在生成结构化内容"占位，不把 JSON 原文刷给用户看。这需要前端在增量拼接时识别围栏开头，逻辑很小。

Schema 校验负责格式，引用存在性、对象归属、数值范围由业务校验处理。故事质量建议与硬性校验错误分开显示。

## 7. 首版不做的事

以下都从旧方案里砍掉，不是延后细化，是首版明确不做。

- 候选结果持久化与完整状态机。前端一个 `pending | ready | failed` 够用，`draftRev` 冲突时的候选只在内存里。
- 上游变更提示与依赖版本记录。等分集阶段再评估。
- 台词在剧本与分镜之间的同步。现状是两者零联系，不存在"无提示地失去联系"的风险，因为本来就没有联系。首版明确写"不同步"。
- 上下文压缩与分段。撞上 32,000 字符直接报错并提示缩小范围，比先造一套压缩管线便宜得多。
- 自动格式修复。
- 通用插件开发框架。公共层从角色代码里抽，不先写好再往里填。
- 模型自主调用领域工具、多 Agent、后台编排、完整修订树、跨资料事务、向量检索、独立评价 Agent。

## 8. 上下文装配顺序

共享资料是指可以按需读取，不是每次请求都传全部内容。装配顺序：

1. 用户本轮请求、选中字段和明确约束。
2. 当前对象最新草稿或正式内容。
3. 直接相关的策划、角色、分集或分镜资料。
4. 当前阶段近期对话。
5. 必要时附加相邻场景或镜头，或用户主动选的参考资料。

未定稿内容作为参考时必须显式标记，别把试写设定当成正式事实。装不下关键资料时提示缩小生成范围。

共创请求走用户在设置里选的策划模型，与现有 `askPlanner` 同一套偏好，不另设。

## 10. 验收

### 角色闭环

用已有短剧生成一个角色，然后：

1. 连续聊天三轮调整人物设定，其中至少一轮是纯闲聊不带围栏，确认草稿不动。
2. 手动改一个字段，再让 AI 改另一个字段，确认手改保留。
3. 看差异并定稿。
4. 关闭重开，恢复聊天和资料，再修改已定稿角色。
5. 生成中手动编辑、切换角色、停止、模拟迟到响应，确认没有误覆盖；中途手改那次要看到"请复核"的候选。
6. 模拟非法 JSON、缺失字段、超时和重复确认，确认资料保留且可继续；重复确认不报错不重建。
7. 关闭插件页后确认底层请求真的停止。
8. 同时发起超过并发上限的请求，确认被明确拒绝而不是全部发出。
9. 用旧宿主版本加载新插件，确认因 `minimumWillDeepVersion` 被拒而不是运行时报未知命令。

第一步只针对单个角色，阶段内批量生成角色随后补充。

### 推广顺序

角色闭环跑通、公共层抽出来之后，依次接入：

- 策划迁入同一套草稿和保存机制，用上 Drama 顶层的 `rev` / `draft`。
- 分集剧本，验证按集或场景生成和长文本编辑。
- 分镜剧情和台词，明确与剧本的来源关系。
- 首尾帧描述；用户定稿后再显式调用已有媒体生成能力。生成文字不自动发起付费图片或视频任务。

每接一个阶段跑真实对话和预览流程，不只测 Schema 能否解析。前端用现有 Yarn 与 Vitest，后端沿用 Ruby 测试脚本，涉及宿主改动再跑 Swift 测试和构建。真实模型验证的调用范围和费用另行安排。

"先做角色"是验证顺序。用户的目标包含全部创作阶段，不能把后续阶段长期留在只能人工编辑的状态后宣称完成。

## 11. 已知风险

- `dramas.json` 单文件加 100 部上限，`draft` 字段会让文件明显变大，每次保存是全量重写。首版接受，记为已知的写放大点。
- 两仓分叉。不先定唯一源，X、R、U 三阶段的产出会立刻再分叉一次。
- `ui/dist` 提交纪律。
- 32,000 字符含 system，分集剧本阶段很快会撞上，届时是硬失败不是降级。
- 围栏协议依赖模型听话。不同 provider 对"把 JSON 放进指定围栏"的服从度不一样，U3 的解析要容忍围栏名大小写和前后空白，这是现有 `parseDramaPlan` 已经在做的。
