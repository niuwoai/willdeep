# Agent 执行摩擦审计（2026-08）

> 审计时间：2026-08-22 | 代码基线：1.284.0-rc2（审计起点）→ 1.284.0-rc6（三项修复落地后）
> 数据来源：本机 `~/Library/Application Support/WillDeep/` 下 459 个落盘会话与 `AgentAudit/judge.jsonl`
> 姊妹文档：[SYSTEM_PROMPT_AUDIT_2026_07.md](SYSTEM_PROMPT_AUDIT_2026_07.md)（缓存命中率）、[LONG_HORIZON_AUTONOMY.md](LONG_HORIZON_AUTONOMY.md)（续推契约）
> 本文只记录**用户能感觉到的三处摩擦**：证据、根因、已落地的修复、以及还没做的部分。

---

## 0. 三句话结论

1. **"计划做得积极，却经常标不上完成"**——不是模型偷懒，是宿主读不懂它的进度上报。539 个 `progress` 块里 58% 一条状态都解析不出，其中最大的一类格式**是提示词自己教给模型的**。
2. **"等待宿主放行"**——产品里没有"宿主"这个角色，是提示词写了 `host-coordinated` / `host-owned`，模型直译后转述给用户，于是用户去找一个不存在的按钮。
3. **"规划完成后还要点"**——Goal 模式设计上确实不用点，但命令类工具要过 AI 安全裁判，而**裁判有 24% 的时候不在岗**（八月以来 826 次裁决中 204 次 `unavailable`），一掉线就静默回落人工审批。

前两条已修（1.284.0-rc3 / rc4），第三条只完成了取证，修复方案见 §3.4。

## 1. 进度记账：58% 的上报是哑弹

### 1.1 证据

全量扫描 459 个落盘会话（脚本见 §5）：

| 指标 | 数值 |
|---|---|
| 模型发出的 `progress` 块 | 539 个（覆盖 91 个会话） |
| 旧解析器能记上账的 | 227 个（42%） |
| **一条都解析不出（白写）** | **312 个（58%）** |
| 带计划的会话 | 115 个 |
| **计划处于"已就绪/执行中"却 0 步标记完成** | **79 个（69%）** |

最典型的标本是会话 `6C2D2D8A`（"完成 SSO 系统开发"）：1284 条消息、622 次工具调用、模型明确宣布"端到端验证完成"，而**计划 11 步全程 `pending`**。

### 1.2 根因

旧合同只认 `1: done`——序号后**紧挨着**状态词（`AgentPlanParser.applyProgress`）。失败样本几乎都是信息齐全、只是排列不同的自然写法：

| 样本 | 为什么读不出 |
|---|---|
| `1. [failed] 实现扫雷模块及回归用例：…` | **占比最大**。状态词被方括号包着——而这正是提示词注入活跃计划时用的格式（`1. [in_progress] 步骤名`），模型照抄天经地义 |
| `1. 实现扫雷模块及回归用例 —— done` | 序号对、状态词对，但状态词落在行尾，解析器读到的是步骤名 |
| `- 实现记忆翻牌模块及回归用例: done` | 用步骤名代替了序号 |
| `step 1: closed` | `closed` 不在状态词表里 |
| `1. 迁移脚本 —— 完成` / `… ✅` | 中文状态词与 `✅` 都不认（旧表只有英文加 `✓`/`✔`） |

**"我们自己教的格式自己不收"是这个 bug 里最贵的一条**：它一条就占了修复收益的三分之二。

### 1.3 后果链

宿主读不出 → 计划停在 `pending` → 续跑策略按"无进展"计数 → `reconcileProgress` 纠偏一轮 → 仍读不出 → `pauseAfterNoProgress` 硬停，或撞满 8 轮 `pauseAfterLimit`。用户看到的就是那句"计划状态同步已暂停……这不代表执行失败"，以及一个再也推不动的死任务。

更糟的是，1.251.0-rc1 落地的退避阶梯（`AgentGoalContinuationPolicy`，永不硬停、只升级话术）**入口第一句就是 `guard runtime.currentPlan?.status == .done`**——计划标不成完成，就永远进不了退避阶梯。新机制被旧的格式合同挡在门外。

### 1.4 已落地（1.284.0-rc3）

`AgentPlanParser` 改三层回退，每层都要求状态词落在**不可能是叙述**的位置：

1. 严格合同 `1: done`，并剥掉 `[]` / `()` / `「」` 等包裹符；
2. 序号对 + 状态词落在行尾；
3. 用步骤名代替序号，且**只有唯一命中一个步骤时才采信**。

状态词表补齐 `closed`/`resolved`/`verified`/`passed` 与中文状态词、`✅` 记号。

**实测（同一批 539 个真实块回放）：42% → 84%，白写 312 → 81，救回 231 个。**

防误判用例同样入库：`1. 修好 CI 上 failed 的那几个用例后再继续` 整行跳过、`99: done` 不被文本匹配捡回、同时命中两个步骤名一律放弃。

### 1.5 未做

`LONG_HORIZON_AUTONOMY.md` §4 的 `update_plan` 工具化是根治方案（provider 侧 schema 校验 + 失败回灌重试，比宿主解析自由文本可靠一个数量级）。本轮只做了解析器止血，围栏块仍是唯一写入通道。

**另一件独立的事**：退避阶梯的入口条件（§1.3 那个 `guard`）应当放开，让计划未标完成时也走退避而不是硬停。它属于 `LONG_HORIZON_AUTONOMY.md` 的 XA1，改动面比解析器大，本轮未动。

## 2. Goal 门禁：一个不存在的"宿主"

### 2.1 证据

用户截图里模型写道：「执行类工具（含可见终端）均被 Goal 计划拦截，只读工具正常……**等待宿主放行后立即执行**。」

### 2.2 根因

Goal 模式在计划验证完成前锁写类工具（`goalPlanningGateBlocks`：`risk != .read` 一律直接 `denied`，不弹审批卡）。这个门禁本身是对的，问题在措辞：

- 系统提示词：`Goal Teams planning is **host-coordinated** and write-tier tools are locked.`
- 拦截回灌：`Finish the **host-owned** planning flow without asking for user approval.`

模型把 host 直译成"宿主"，于是对用户宣布自己在等放行。可现实里既没有这个放行动作，也没有对应按钮——用户去找一个不存在的控件，模型在原地空转。

`blocked` 阶段更糟：旧提示词只允许模型"解释证据缺口"，不许出计划也不许执行，于是它反复解释、反复被拒。而 Goal 卡片上那个**「重试规划」按钮一直都在**，从来没人提过一句。

### 2.3 已落地（1.284.0-rc4）

- 门禁措辞整体去 host 化，文案集中到 `AgentGoalGateNotice`；
- 明确写死"该干什么"：这是后台自动流程、没有人需要批准、催也不会更快，与其空等不如继续只读取证；
- **明令禁止**模型宣称自己在等待放行/批准/授权；
- `blocked` 阶段要求说清哪个成员失败、缺什么证据，并指向「重试规划」或收窄目标；
- 工具卡文案本地化为「Goal 规划进行中，工具暂时锁定——你不需要做任何操作」（en/zh-Hans/ja/es/fr）。

按既有约定（正规通道已存在时只把话讲清楚），**没有新增任何 UI**。

## 3. 审批裁判：24% 的时间不在岗

### 3.1 客户反馈

> 「goal 模式还得迭代迭代，就是完全控制模式」「我用 trae 感觉不错，不用点」

### 3.2 设计上本该怎样

Goal 模式已经相当自主（`autoApprovalSource`）：

- 沙箱内、非命令形的写操作（文件写、已验证的公网 `web_fetch`）→ 直接 `.goalMode` 放行；
- **命令形工具**（`run_command` / `terminal_*` / `call_mcp_tool`）→ 走静态分类 + AI 安全裁判；裁判 `allow` 就自动放行；
- 危险级、需要打字确认的操作 → 永远要用户确认（这是刻意的，不改）。

也就是说：**规划完成后，普通命令本来不该要用户点**。

### 3.3 实际发生了什么

`AgentAudit/judge.jsonl` 全量 1967 条裁决：

| verdict | 全量 | 八月以来 |
|---|---|---|
| `allow` | 1599（81%） | 585（70%） |
| **`unavailable`** | **305（15%）** | **204（24%）** |
| `deny` | 63（3%） | 37（4%） |

每一次 `unavailable` = 一次本可自动放行、却弹给用户点的审批卡。掉线原因：

| 原因 | 次数 | 说明 |
|---|---|---|
| `missing api key` | **211（69%）** | 裁判模型（`deepseek-v4-flash`）根本没配 key |
| `no verdict tag` | 30 | 裁决被截断成半截（见 §3.5） |
| `empty reply` | 20 | |
| `network error` | 19 | |
| `http 404` | 17 | |
| 其余 | 8 | 422 / 502 / fallback 组合 |

涉及模型：`deepseek-v4-flash` 226 次、`someim-security-guard` 54 次、`someim-auto-flash` 25 次。

**结论：客户说的"还要点"完全属实，但根因不是产品设计要他点，而是裁判有四分之一的时间不在岗，一掉线就静默回落人工。** 其中 86%（261/305）是纯工程问题，与安全判断本身无关。

### 3.4 建议修复（未做）

1. **没配 key 就不该被选作裁判。** 保存设置时校验凭据，缺失即在设置页显式报错，并自动回落到已配置的 provider——而不是等到用户干活时才静默降级。
2. **掉线要说出来。** 审批卡上写明"因为安全裁判不可用才需要你确认"，附一个跳到裁判配置的入口。用户现在完全不知道自己多点的这些是可以消除的。
3. **`no verdict tag` / `empty reply` 是输出预算问题**，见 §3.5。

### 3.5 与已知问题的关系

`no verdict tag`（30 次）与内部已记录的现象一致：裁判普遍是推理模型，输出预算不够时会把裁决截断成半截 `<verdict>YES`，宿主解析不出就静默回落人工，**命令越复杂越容易掉线**。修法是给裁判请求单独设置足够的输出预算并对半截裁决重试，而不是把它当作"裁判说不行"。

## 4. 提示词体量：对标 willdeep-rs

### 4.1 现状对比

| | Xedit（本轮前） | willdeep-rs 0.39.0-rc3 |
|---|---|---|
| 提示词文本总量 | 212k 字符 / 散落 23 个文件 | `prompt.rs` 全文 145 行 |
| 稳定契约主体 | `Stable tool contract` 单块 15,677 字符 / 32 条 | `STABLE_CONTRACT` ≈4,600 字符 |
| 最长单条 | **2,010 字符**（终端路由，一条塞了 12 种边界情况） | 无超过 400 字符的条目 |
| 组装方式 | 按 profile + capability 动态拼装，v29 + 三个快照哈希守卫 | 4 个静态小节 + 2 行动态上下文 |

三档稳定前缀的实测体量（`toolsEnabled: true`）：

| profile | 本轮前 | 本轮后 | 变化 |
|---|---|---|---|
| compact | 4,531 | 4,531 | 未动（已经和 rs 同一量级） |
| standard | 18,555 | 16,582 | **−10.6%** |
| extended | 20,441 | 18,468 | **−9.7%** |
| extended + 全部 capability | 24,139 | 22,166 | −8.2% |

### 4.1.1 沉积速率：这不是第一次瘦身

`willdeep-agent-system-v26` 那一轮已经做过一次**按能力门控**的瘦身：浏览器/UI QA、Web 编程工作流、computer-use 协议三块移入能力附录，standard 从 20,938 压到 **17,494**（−16.5%），且刻意保证"附录严格追加在稳定核心之后，核心字节序全局不变"——前缀缓存因此没有被破坏。

而本轮开工前 standard 是 **18,555**。也就是说 **v26 之后又长回了 1,000 字符**。提示词是会沉积的：每处理一次事故就追加一段，没有人会回头删。终端路由那条 2,010 字符的 bullet 就是十几次踩坑叠出来的化石层。

**这意味着"精简"不是一次性任务，而是需要一条抑制沉积的规则**（例如：新增边界约束优先写进工具报错文案，写进稳定核心需要说明为什么必须每轮都付这份 token）。

> ⚠️ 与 v26 不同，本轮改的是**稳定核心本身**（v29 → v30），所有用户的 provider 前缀缓存会一次性失效并在下一轮重建。这是版本升级的正常代价，但也是为什么后续应优先走"下沉到附录/报错文案"而不是继续重写核心。

### 4.2 两个反直觉的观察

1. **越强的模型收到越长的提示词。** `AgentSystemPromptProfile.automatic` 把 opus / gpt-5.5 / gemini-3 归到 `extended`（最长档），小模型才走 `compact`。真正需要手把手教的是小模型。
2. **`compact` 档已经自证了精简空间。** 同样的工具契约，compact 用 6 条 bullet 讲完，standard/extended 用 32 条，信息覆盖度差得并不多——而 compact 的 4.5k 字符恰好与 rs 的完整契约同一量级。

### 4.3 本轮做了什么

按"压缩表达、不删语义"的原则重写，合并同类项。整块 `Stable tool contract` 从 **15,677 字符 / 32 条**降到 **14,121 字符 / 31 条**：

| 组 | 前 | 后 |
|---|---|---|
| 终端（路由与主机身份 / dispatch 确认不是输出 / 别用 heredoc 造文件） | 3 条 2,861（最长一条 **2,010**） | 3 条 2,012（最长 1,071） |
| `create_file`/`edit_file`（工具用法 / 字面文本 / 补丁卡去向） | 1 条 1,656 | 3 条 1,361 |
| MCP + Lark + DingTalk | 5 条 1,241 | 3 条 1,134 |
| 图片生成 | 2 条 763 | 1 条 523 |
| 失败调试、后台任务、front-load 沟通 | — | 各压 20–30% |

**每一条被压缩的规则，其约束核心都保留了**：守卫测试里那些精确字符串断言（`result stale`、`Never edit source code, build configuration`、`${{ secrets.NAME }} reference is not the secret value`、`Diagnose, repair, retry, and continue`）**一条都没有为了省字数而改动**——反倒是重写时把措辞调了回去。改动让三个快照哈希全部重录（standard 与 extended 因文本变化，compact 因版本号字符串本身在提示词里），这正是守卫该有的行为。

### 4.4 未做：结构性精简

继续抠字数的边际收益在快速下降，风险却线性上升——那些边界情况几乎每条背后都是一次真实事故。要再往下走，应该做**结构性**改动而不是继续压缩：

1. **把边界情况从提示词移到工具报错文案。** 模型犯错的当下才是教它的最佳时机，而不是每轮都付一遍 token。终端路由那 12 种情况绝大多数适合这么处理。
2. **扩展 capability appendix 的覆盖面。** 机制已经有了（`AgentPromptCapabilities`），目前只管 browser / webCoding / computerUse 三项。终端、MCP、图片生成都可以按"工具是否在列"下沉——**v26 那轮证明了这条路收益更高（−16.5%）且不破坏前缀缓存**，比重写稳定核心划算。
3. **重新评估 profile 与模型能力的对应关系**（§4.2 第 1 点）。

## 5. 复现方法

三份取证脚本都是只读的，直接对着 `~/Library/Application Support/WillDeep/` 跑：

- **进度块解析率**：遍历 `agent-sessions/*.json` 的 assistant 消息，抽出 ` ```progress ` 与 `<progress>` 块，用新旧两套规则分别解析，统计"至少记上一条"的块数。
- **计划完成度**：同一批会话里读 `currentPlan.status` 与各步 `status`，统计"已就绪/执行中但 0 步终态"的比例。
- **裁判可用率**：`AgentAudit/judge.jsonl` 按 `verdict` 与 `detail` 分组计数。

`judge.jsonl` 里查不到某次审批，说明裁判压根没上场——被前置门禁拦下了，那是另一条路径。
