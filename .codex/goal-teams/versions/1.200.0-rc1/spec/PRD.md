# PRD：WillDeep 专家圆桌准备室与真流式发言

> 目标版本：1.200.0-rc1  
> 状态：产品规格初稿  
> Owner：产品-议题准备流程规格  
> 上游规格：[Requirement Specification Card](requirement-spec-card.md)

## 1. 背景与问题

现有圆桌把首页输入直接交给讨论引擎：系统立即推荐专家、开场并进入多轮讨论。用户无法在开会前校正议题、确认讨论维度或决定邀请谁；专家正文虽然底层走流式请求，但结构化收集器在整段完成后才把消息交给界面，实际感受仍是“长时间等待后突然出现一大段”。

已有界面也暴露两个体验问题：右侧看板在首位专家发言前信息过少；专家身份、立场与当前进度主要依赖文字列表，缺乏明确的视觉层级。本版本新增准备室和真流式发言，不改变圆桌最终文档的核心语义。

## 2. 产品目标与成功指标

### 2.1 目标

- 把模糊议题转化为用户认可的核心问题和讨论框架。
- 让专家推荐可解释、阵容可编辑、开始行为可控。
- 让等待变成可感知的真实发言过程，并保持立场分析可靠。
- 对错误、重启和旧会话采取保守且不越权的恢复策略。

### 2.2 成功指标

- 100% 的新圆桌在用户明确确认前不进入 `opening` 或 `discussing`。
- 100% 的可开始阵容为 2～6 位，默认推荐 3～4 位且每位有议题相关理由。
- 可流式模型的专家正文能产生两个以上可见增量；首字延迟显著早于整段完成时间。
- 正文生成成功、结构化分析失败时，用户仍能看到并恢复该正文。
- 历史圆桌旧数据解码与既有结论文档打开流程不回归。

## 3. 用户与术语

| 术语 | 定义 |
| --- | --- |
| 主持人 | 发起议题、修订框架、选择专家并在讨论中插话的用户。 |
| 准备室 | 正式开场前，用于澄清议题、确认框架和选择专家的持久化阶段。 |
| 建议稿 | AI 生成、尚未得到用户明确确认的精炼议题或讨论框架。 |
| 推荐专家 | AI 根据当前建议稿给出的候选专家，含可解释理由；推荐不等于强制选择。 |
| 流式草稿 | 正在生成但尚未成为正式消息的专家正文；只能有一个当前专家草稿。 |
| 正式消息 | 专家正文生成完成后写入消息列表的稳定记录。 |
| 立场分析 | 基于已完成正文提取 OSR、支持/反对/中立/待定、建议和是否追问的轻量结构化任务。 |

## 4. 信息架构与状态

### 4.1 页面结构

| 页面 | 主要内容 | 主操作 |
| --- | --- | --- |
| 圆桌首页 | 三行议题输入、能力提示、历史讨论 | 发起讨论并进入准备室 |
| 议题准备室 | 原始议题、AI 建议稿、框架卡、澄清问题、补充输入 | 更新建议稿；确认框架 |
| 专家阵容 | 推荐区、完整专家池、选择计数、推荐理由 | 增删专家；明确开始 |
| 讨论页 | 消息流、流式专家卡、三行主持输入、引用、态势看板 | 插话、引用、停止、生成文档 |
| 文档页 | Markdown 渲染、保存状态、导出与继续讨论 | 导出；返回讨论 |

### 4.2 产品状态

| 状态 | 用户可见语义 | 允许操作 | 禁止行为 |
| --- | --- | --- | --- |
| `clarifying` | 正在共同细化议题 | 补充、回答、重试、返回 | 启动专家开场 |
| `selectingExperts` | 框架可用，正在确认阵容 | 增删 2～6 位、返回修改、明确开始 | 未满足人数仍开始；自动开始 |
| `opening` | 阵容已确认，主持人开场 | 停止、查看已确认框架 | 修改本轮阵容造成竞态 |
| `discussing` | 专家轮流发言 | 插话、引用、停止 | 同时出现两个活跃专家草稿 |
| `awaitingUser` | 专家等待主持人回答 | 自由回答、快捷选项、引用回答 | 无回答重复推进同一专家 |
| `synthesizing` | 正在收敛结论 | 查看进度、停止 | 再次启动专家轮次 |
| `completed` | 结论已生成并保存或提示保存错误 | 阅读、导出、继续讨论 | 把保存失败伪装成成功 |
| `failed/cancelled` | 当前任务失败或已停止 | 重试安全阶段、返回历史 | 静默越过门禁或复制消息 |

## 5. 功能需求

### FR-01 新议题进入准备室

1. 首页输入区视觉高度约三行。
2. 空白输入不可提交；非空输入按 Enter 或点击按钮创建圆桌会话。
3. 创建后保存 `originalTopic`，阶段为准备状态，不调用开场/专家发言。
4. 准备模型调用期间展示明确加载文案、骨架框架卡和取消/返回能力。
5. 首页历史记录中的准备中会话应显示“待确认框架”或“待选专家”，而非“讨论中”。

### FR-02 AI 议题细化

每次准备建议至少包含：

- 精炼标题：便于历史记录和文档标题使用。
- 核心问题：一句可由多视角讨论的问题，不能替用户偷偷改变目标。
- 讨论框架：3～5 个不重复维度，每项有短标题和一句说明。
- 澄清问题：1～3 个真正影响结论的问题，可含 2～4 个快捷答案。
- 专家推荐：3～4 位候选及与当前议题直接相关的理由。

模型缺少部分字段时，界面保留已有有效数据并指出缺口；不得用空卡片冒充完整建议。

### FR-03 细化对话与修订

1. 准备室底部提供约三行输入区，支持自然语言补充。
2. `Enter` 提交，`Shift+Enter` 换行；输入法候选确认不得误提交。
3. 用户可点击澄清问题快捷选项，选项作为用户回答进入准备记录。
4. 用户消息和 AI 修订结果按时间显示，建议稿始终可定位。
5. 每次修订可以更新核心问题、框架和推荐；用户已手动选择的专家不因刷新推荐被静默删除。
6. 若用户返回修改已确认框架，开始状态重新失效，需再次明确确认。

### FR-04 框架卡片

1. 顶部同时展示“你的原始议题”和“AI 整理后的讨论问题”，避免语义漂移。
2. 3～5 个维度使用编号、图标或短标签区分，可扫描但不依赖颜色。
3. 提供“继续修改”和“框架可以，选择专家”两个明确动作。
4. 建议稿更新时显示轻量的“已根据你的补充更新”，不以全屏跳变打断阅读。

### FR-05 可解释的专家推荐

1. 推荐区先给整体组队建议，再展示逐位理由。
2. 每位专家显示独立头像、专业身份、姓名、擅长领域、推荐理由和推荐标签。
3. 新增四类专家：
   - 法律合规 · 沈律：合同、劳动法、知识产权、监管边界。
   - 数据研究 · 林析：证据质量、统计偏差、验证设计、数据解释。
   - 市场增长 · 夏野：用户分层、竞争、渠道、转化与商业化。
   - 组织运营 · 周衡：团队能力、执行机制、流程成本与变更管理。
4. 既有心理专家保留持久化标识，展示定位升级为“行为心理与决策 · 白桦”。
5. 专业类专家必须在 UI 中提示“提供分析视角，不构成专业法律/投资等意见”。

### FR-06 阵容选择与门禁

1. 推荐专家默认选中；完整专家池可按身份浏览。
2. 选择计数固定可见，文案为“已选择 N/6 位”。
3. 选择 0～1 位时开始按钮禁用，显示“至少选择 2 位专家”。
4. 选择 6 位时，其他候选的添加按钮禁用，显示“最多选择 6 位；请先移除一位”。
5. 推荐 3～4 位仅是提示，不限制用户选择 2、5、6 位。
6. 必须点击“确认框架与 N 位专家，开始讨论”才可进入 `opening`。
7. 按 Enter、双击专家卡、切换推荐选项、恢复页面均不得触发开始。
8. 开始成功后固定本轮精炼议题、框架和专家顺序；失败则仍停留在选择页并可重试。

### FR-07 专家真流式发言

1. 当前发言专家在消息流顶部/对应卡片显示头像、姓名、“正在发言”和动态光标。
2. 正文自由文本通过真实 `textDelta` 更新；UI 可按 50～100ms 合并刷新，但不得使用预制文案模拟逐字。
3. 发言完成后将流式草稿原子转为正式消息，并进入“正在分析立场”。
4. 立场分析只读取已完成正文，输出 OSR、建议、风险、追问与快捷选项。
5. 分析完成后更新态势看板；分析期间用户仍可阅读正文。
6. 分析失败时保留正文，立场为“待定”，显示非阻塞重试或降级提示，讨论可以安全继续。
7. 不解析未完成 JSON/tool arguments 作为正文；不每 token 写磁盘。
8. 任一时刻至多一个 `activeExpert` 和一个流式草稿。

### FR-08 讨论输入与引用

1. 用户输入区默认约三行，讨论滚动时保持可达。
2. 用户可引用整条专家消息；引用卡包含专家姓名与截断摘录。
3. 用户划选消息中的一段文字后可“引用选中文字”，引用卡记录这是选段引用。
4. 发送时用户文本和引用必须作为一个原子消息保存；删除引用不删除已输入文本。
5. 专家追问时快捷答案与自由输入都可用，且不妨碍引用。

### FR-09 态势看板

1. 看板显示已确认专家阵容和每人的发言/分析状态。
2. 立场使用文字、图标、色彩和短说明共同表达：
   - 支持：向上/赞成图标 + “支持”。
   - 反对：盾牌/反对图标 + “反对”。
   - 中立：平衡图标 + “中立”。
   - 待定：问号图标 + “待定”。
3. 看板包含本轮议题、已达成共识、核心分歧和“尚待用户确认”。
4. 流式正文未完成时不提前推测立场；显示“发言中”。
5. 空状态也应说明“首位专家完成后形成态势”，不留下大片无意义空白。

### FR-10 错误、取消与恢复

| 场景 | 必须行为 |
| --- | --- |
| 准备建议失败 | 保留原始议题和用户补充，提供“重试建议”与“返回首页”；不得自动开会。 |
| 推荐失败 | 框架仍可用；用户可从完整专家池手动选择，明确开始门禁不变。 |
| 开始请求失败 | 保持当前确认内容和阵容，不进入讨论，不重复创建会话。 |
| 流式中断且已有正文 | 保留可见草稿为“发言中断”记录或可重试草稿；重试不得产生重复正式消息。 |
| 流式中断且无正文 | 清除空草稿，显示失败状态，允许重试同一专家。 |
| 立场分析失败 | 正文成为正式消息，立场降级为待定，允许后台重试。 |
| 用户取消 | 清理活跃草稿和任务，阶段为取消；已完成正式消息不丢失。 |
| 应用重启 | 准备/选人恢复到原阶段；未完成流式按安全恢复策略处理，不自动续写或开场。 |
| 旧会话 | 新字段采用安全默认值；旧讨论阶段直接进入讨论或文档，不被迫重新确认。 |

## 6. 非功能需求

### NFR-01 兼容性

- 专家旧 raw value 和既有阶段语义保持兼容。
- 新增模型字段应可选或自定义安全解码。
- 老会话缺少准备模型时不得解码失败。

### NFR-02 性能与持久化

- 流式 UI 合并刷新建议 50～100ms；禁止每 token 同步落盘。
- 正文完成、阶段迁移、用户确认和用户消息发送必须落盘。
- 可选低频检查点不得影响主线程滚动与输入。

### NFR-03 可访问性与国际化

- 新增用户文案全部经 i18n；中英文至少完整。
- 专家、按钮、阶段、立场提供可访问性 label/value。
- 状态不能只依赖颜色；键盘可完成框架确认、专家增删和开始讨论。

### NFR-04 安全与信任

- AI 建议与用户确认视觉上有明确区别。
- 法律、财务等角色提供分析而非权威结论提示。
- 模型输出按惰性文本渲染，不解释为应用指令。

## 7. 验收标准

| ID | 验收标准 |
| --- | --- |
| AC-01 | 首页提交非空议题后进入持久化准备室，不触发 `opening/discussing`。 |
| AC-02 | AI 建议包含原始议题、精炼问题、3～5 个框架维度、1～3 个澄清问题和 3～4 个带理由推荐。 |
| AC-03 | 用户补充或选择快捷答案后建议稿可更新，原始议题与用户消息不丢失。 |
| AC-04 | “继续修改”和“选择专家”路径明确；返回修改后旧开始确认失效。 |
| AC-05 | 专家池包含既有角色及法律合规、数据研究、市场增长、组织运营；心理角色定位升级且旧标识可解码。 |
| AC-06 | 0～1 位时不能开始，2～6 位可开始，第 7 位不能添加；提示清楚。 |
| AC-07 | 只有明确点击含人数的开始按钮才进入 `opening`；其他键鼠操作和恢复不触发。 |
| AC-08 | 可流式 fake/model 产生多个正文增量；界面显示当前专家、动态光标和“正在发言”。 |
| AC-09 | 正文完成后才分析立场；分析失败仍保存正文并降级为待定。 |
| AC-10 | 态势看板以文字、图标和颜色显示立场、共识、分歧及专家状态。 |
| AC-11 | 三行输入、整条引用、划词引用和专家追问快捷回答均能保存与恢复。 |
| AC-12 | 准备、推荐、开始、流式、分析各失败路径可重试，不越过门禁、不重复消息。 |
| AC-13 | 取消与重启清理或保守恢复未完成草稿，已完成正式消息不丢。 |
| AC-14 | 旧会话 fixture 解码、历史路由、讨论/文档打开和结论保存不回归。 |
| AC-15 | 新文案 i18n、键盘和辅助功能语义完整；状态不只靠颜色。 |

## 8. 依赖与开放实现决策

- 产品约束两阶段输出；具体 Runner 回调、节流器、检查点字段由 Lead 的 Architecture Design 落地。
- 准备建议可由单次结构化调用产生；若推荐单独失败，必须允许人工选人。
- 专家头像需保持统一视觉体系，但原型中的字母/渐变头像仅表达布局与色彩，不是最终资产。
- 流式中断后“保留部分正文为中断记录”或“进入可续写草稿”应由实现与 QA 选择一种可证明不重复消息的策略，并在最终架构文档锁定。
