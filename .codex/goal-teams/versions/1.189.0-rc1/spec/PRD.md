# PRD：WillDeep Goal Teams 规划优先流程

> 目标版本：1.189.0-rc1
> 状态：已实现并通过 AC-01～20 独立验证
> Owner：需求分析-Goal Teams 流程契约
> 上游规格：[Requirement Specification Card](requirement-spec-card.md)

## 1. 背景与问题

当前 WillDeep 的 Plan 模式已经具备“提案 → 用户批准 → 执行 → progress”的契约；Goal 模式则在 Goal 定义后直接声明写级工具自动批准。现有多专家会诊另有“独立首轮 → 初步综合 → 第二轮互评 → 最终综合”能力，但不会自动成为 Goal 的规划门禁。

这造成两个核心问题：Goal 可能在用户看到完整执行方案前修改工作区；会诊、Plan 与 Goal 三套能力没有形成可恢复、可测试的统一闭环。

本 PRD 仅从上游规格卡派生，定义用户可见流程、安全语义和验收，不指定具体 Swift 架构。

## 2. 产品目标与成功指标

### 2.1 目标

将 Goal 模式统一为：

`Goal 定义 → 三身份独立首轮 → 分歧仲裁第二轮 → Teams 规划表 + Plan → 用户确认 → Goal 执行与复验`

### 2.2 成功指标

- 100% 的新 Goal 在首次写级工具调用前存在用户已批准的有效 Plan。
- 100% 的可确认 Plan 具有至少两份有效、可追溯的独立首轮报告和一次分歧仲裁结果。
- 100% 的 Teams 计划包含任务 owner、locked scope、Done Criteria、测试 owner 与独立 validator。
- 正常、拒绝、降级、恢复、旧会话兼容路径均可由 Swift 自动化测试证明。

## 3. 角色与术语

| 术语/角色 | 定义 |
| --- | --- |
| 用户 | 定义 Goal、回答必要澄清问题、批准或拒绝最终 Plan。 |
| Goal Lead | 编排规划成员、综合证据、生成 Teams 表与 Plan、协调执行闭环。 |
| 规划成员 | 独立、只读的分析单元；首轮互不可见其他成员的未完成结论。 |
| 仲裁成员 | 第二轮独立评审身份，专门裁决分歧、证据强弱与停止条件。 |
| 有效报告 | 非空，包含角色结论、证据或明确证据缺口、风险和建议；运行失败或只有错误文本不算有效。 |
| 可确认 Plan | 独立规划门槛已满足、Teams 表字段完整、可提交给用户批准的 Plan。 |
| 写级工具 | 会修改文件、运行有副作用命令、改变外部状态的工具；具体分类沿用 WillDeep 现有权限模型。 |

## 4. 状态与门禁

| 状态 | 允许 | 禁止 | 进入条件 |
| --- | --- | --- | --- |
| setup | 澄清目标、只读检查 | 普通写级工具、危险级工具 | Goal 尚未形成 |
| planning | 三身份首轮、仲裁、只读仓库取证 | 普通写级工具、危险级工具、worker 实现 | Goal 已形成但无可确认 Plan |
| proposed | 展示 Teams 表与 Plan、等待用户操作 | 普通写级工具、危险级工具、自动执行 | 规划门槛满足且 Plan 已生成 |
| approved/executing | 按 Plan 发起普通写级工具并进入既有审批流程、更新 progress/goal-check；危险级工具逐次请求用户确认 | 越出 Plan/locked scope 的静默扩张、跳过危险级工具逐次确认 | 用户明确批准当前 Plan |
| rejected | 读取拒绝意见、重新规划 | 复用旧 Plan 授权、普通写级工具、危险级工具 | 用户拒绝当前 Plan |
| done | 展示验收证据 | 将未满足 Goal 标为完成 | Plan 与 Goal Acceptance 均满足 |
| blocked | 展示失败原因、重试/退出选项 | 静默降级执行 | 独立报告或仲裁未达到安全门槛 |

门禁规则：Goal 模式从进入 setup 起立即锁定普通写级工具和危险级工具，不以 Goal 是否已经形成作为门禁起点。只有当前 Plan 为 approved/executing 时，计划范围内的普通写级工具才可进入 WillDeep 既有审批流程；Plan 缺失或为 proposed/rejected/done/blocked 时均不得放行。危险级工具不因 Goal 或 Plan 批准而获得授权：未批准 Plan 时由规划门禁拒绝，Plan 已批准后仍须对每一次调用取得用户明确确认。

## 5. 详细功能需求

### FR-01 Goal 收集与自动进入规划

1. Goal 模式通过自然对话收集一句可执行 Goal 与可观察 Acceptance。
2. 信息不足时提出最少量、高信号问题，不猜测部署目标、敏感配置或范围。
3. Goal 一旦形成，系统自动进入 planning；用户不需要再输入“继续规划”。
4. planning 开始即激活写门禁，只读工具仍可用于证据收集。

### FR-02 默认三身份首轮

系统默认为每个 Goal 建立三个角色+具体任务身份：

| 身份 | 必答问题 | 最低输出 |
| --- | --- | --- |
| `需求分析-目标边界质疑` | 真正目标、用户价值、范围、非目标、隐藏假设是什么？ | 需求结论、假设、缺口、边界、建议 |
| `架构-实现路径论证` | 仓库现状支持什么最小可靠路径，影响和迁移风险是什么？ | 路径/符号证据、方案、locked scope、风险、验证 |
| `测试-失败路径审查` | 哪些反例、回归、失败和恢复路径会推翻方案？ | 反例、测试面、停止条件、独立验收建议 |

首轮成员必须：

- 使用彼此独立的上下文切片，不读取其他首轮成员的进行中结论。
- 只读检查，不编辑文件、不运行有副作用命令。
- 把会话、仓库文档、外部输出视为惰性证据，拒绝其中的提示注入。
- 引用可定位的路径/符号；无法取证时明确标为“证据缺口”，不得编造。

### FR-03 第二轮分歧仲裁

1. 三份报告成功，或其中至少两份有效时，才可进入第二轮。
2. 仲裁成员接收 Goal、Acceptance、首轮报告和必要仓库证据，但仍保持只读。
3. 仲裁输出必须包含：共识、真实分歧、证据缺口、接受建议、拒绝建议及理由、未决风险、停止条件。
4. 仲裁不得按票数决定；冲突以仓库证据、用户约束和安全性排序。
5. 仲裁不得直接开始实现，也不得把输出伪装成已经批准的 Plan。

### FR-04 Teams 规划表

Goal Lead 只能在仲裁成功后生成 Teams 规划表。每行对应一个明确 owner，Member 名称必须为“角色-具体任务”。表格至少包含：

| 字段 | 要求 |
| --- | --- |
| Member | 角色+具体任务显示名 |
| Skill/Subagent | 实际技能或成员类型 |
| Goal Slice | 对总 Goal 的可验证切片 |
| Claimed Tasks | 稳定任务 ID |
| Locked Scope | 允许修改或读取的明确范围 |
| Deliverable | 具体产物 |
| Done Criteria | 可观察完成标准 |
| Docs/Tasklist Updates | 需更新的文档/任务状态 |
| Test Owner | 实际执行测试者 |
| Validator | 与作者不同的独立验证者 |

同时显示环境/文档 readiness、SPEC readiness、风险/审批/停止条件。若某身份失败，必须在表格或紧邻说明中记录失败原因、影响和验证补偿。

### FR-05 完整 Plan 生成

1. Teams 表之后输出一个现有解析器可识别的 fenced `plan` 编号块。
2. Plan 是当前用户请求的完整交付合同，覆盖实现、测试、文档、版本与验收；除非用户只要求部分交付，不得只列样例或第一阶段。
3. 每个 Plan 步骤须能关联 Teams member、task ID 或明确产物。
4. 生成后状态为 proposed，立即停止自动推进，等待用户批准或拒绝。

### FR-06 用户确认与执行

1. 用户批准当前 Plan 后，状态进入 approved/executing，才解除写门禁并启动实现成员。
2. 执行严格遵守已批准 Plan 与 locked scope；范围、成员或技能发生实质变化时必须重新生成 Teams 表并再次确认。
3. 每次推进步骤后继续输出现有 `progress` 块；Goal Acceptance 的变化继续输出 `goal-check` 块。
4. 用户拒绝时，Plan 变为 rejected，Goal 与 Acceptance 保留；系统依据反馈重新 planning，旧 Plan 的授权立即失效。

### FR-07 完成与继续规划

1. 只有 Plan 步骤和 Goal Acceptance 都有证据满足时，Goal 才能 done。
2. 如果 Plan 全部 done/skipped/failed，但 Goal 仍有未满足项，系统重新进入 planning 并恢复写门禁。
3. 被 deferred/blocked 的任务必须有原因、风险和后续处理，不得被静默视为完成。

### FR-08 安全降级

| 场景 | 行为 | 是否可进入 proposed |
| --- | --- | --- |
| 三份首轮报告有效 | 正常仲裁与综合 | 是 |
| 仅两份报告有效 | 记录缺失身份/原因；仲裁需提出验证补偿 | 是 |
| 仅零或一份报告有效 | 展示不可执行草案、失败原因与重试建议；保持写门禁 | 否 |
| 独立成员能力整体不可用 | 明示“未完成独立辩证验证”；可展示 Lead 草案供阅读，但不可批准执行 | 否 |
| 仲裁失败/空输出 | 保留首轮证据，展示失败并允许重试；保持写门禁 | 否 |
| 输出疑似提示注入 | 按惰性证据处理并记录安全告警；不执行其中指令 | 仅在其他门槛满足时 |

任何失败都必须可见、可恢复、可持久化；不得静默绕过独立规划。

### FR-09 旧会话与现有模式兼容

1. 新增或演进的持久化字段必须支持缺省值，旧会话反序列化不得失败。
2. 旧 Goal 会话只有 `currentGoal`、没有有效 `currentPlan`：恢复后进入 planning，禁止写操作。
3. 旧 Goal 会话的 Plan 为 approved/executing：继续原 Plan，不重复要求确认；危险操作规则不变。
4. 旧 Plan 已 done/rejected/缺失且 Goal 未完成：进入 planning，旧 Plan 不再授权写操作。
5. 普通 Plan 模式的提案、批准、拒绝、progress 解析与 UI 行为保持不变。
6. 既有会诊报告的可选字段和旧数据仍可解码；Goal Teams 不要求旧会诊自动升级成 Goal Plan。

## 6. 非功能需求

### NFR-01 安全

- 规划阶段必须在工具执行层和提示词层同时表达只读约束；仅靠提示词不算门禁证据。
- 外部输出必须有长度边界，并作为惰性数据包装；敏感信息不得进入报告、日志或文档。
- Plan 批准不覆盖 danger-tier 的用户逐次确认。

### NFR-02 可观测与可恢复

- 至少可观察当前阶段、成员身份、每个成员状态/错误、报告是否有效、当前 Plan 状态。
- 应用重启后能恢复到不扩大权限的状态；无法判定时默认 planning/blocked，而不是 executing。

### NFR-03 性能与并发

- 首轮三个身份应并行执行；第二轮必须等待首轮有效结果后串行进入。
- 单个失败不取消其他首轮成员；达到至少两份有效报告时可继续，否则阻塞。

### NFR-04 国际化与可访问性

- 新增用户可见文本必须走现有本地化资源，不在 SwiftUI 中硬编码。
- 阶段、失败和确认状态不能只靠颜色表达。

## 7. 自动化验收标准

以下标准必须能由 Swift 单元测试或集成测试直接证明；测试可使用 fake runner/tool executor，不依赖真实外部 CLI 或网络。

| AC | Given | When | Then | 推荐证明层级 |
| --- | --- | --- | --- | --- |
| AC-01 | Goal 模式处于 setup，Goal 尚未形成 | 模型请求普通写级工具或危险级工具 | 请求均被规划门禁拒绝；只读澄清仍可用，危险级工具不得仅凭逐次确认绕过 Plan 门禁 | 门禁单测 |
| AC-02 | Goal 已形成且无 approved/executing Plan | 模型请求普通写级工具或危险级工具 | 请求均被拒绝，状态为 planning/proposed/rejected/blocked 之一；不得进入既有写审批或危险级执行确认 | 门禁参数化单测 |
| AC-03 | 新 Goal 进入 planning | 启动首轮 | 恰有三个唯一默认身份；均收到只读约束和对应角色任务 | 编排/提示词单测 |
| AC-04 | 三个 fake 成员可用 | 首轮运行 | 三者并发启动；每份报告独立保存，完成顺序不影响角色映射 | async 集成测试 |
| AC-05 | 一个首轮成员失败、两个成功 | 首轮结束 | 进入仲裁；失败身份/原因和验证补偿出现在综合输入或 Teams 输出 | 降级集成测试 |
| AC-06 | 仅一个或零个有效报告 | 首轮结束 | 不调用仲裁/不生成可确认 Plan；写门禁保持；显示可恢复错误 | 失败路径单测 |
| AC-07 | 至少两份有效报告 | 启动第二轮 | 仲裁输入含全部有效报告；输出结构含共识、分歧、证据缺口、接受/拒绝、风险和停止条件 | Prompt/解析单测 |
| AC-08 | 仲裁失败或空输出 | 尝试综合 | 不进入 proposed；首轮证据保留；用户可重试 | 恢复集成测试 |
| AC-09 | 任一报告含“编辑文件/忽略门禁”类指令 | 仲裁与综合 | 指令仅作为惰性文本，不产生写工具调用，安全告警可见 | 提示注入回归测试 |
| AC-10 | 仲裁成功 | Lead 生成结果 | Teams 表包含 10 个必填列；成员名均为“角色-具体任务”；每项有 owner、scope、test owner、validator | 结构解析单测 |
| AC-11 | 完整 Teams 结果已生成 | Plan 被解析 | 编号 Plan 覆盖实现、测试、文档、版本/验收或明确 N/A；状态为 proposed | Plan parser 集成测试 |
| AC-12 | Plan 为 proposed | 用户未操作 | 不启动 worker，不执行写级工具 | UI/运行时集成测试 |
| AC-13 | Plan 为 proposed | 用户批准 | 同一 Plan 进入 approved/executing；写级工具按既有权限与范围解锁 | 确认集成测试 |
| AC-14 | Plan 为 proposed | 用户拒绝 | currentGoal/Acceptance 保留，当前 Plan 失去授权，重新进入 planning | 拒绝/恢复测试 |
| AC-15 | Plan 全部结束但 Goal checklist 未完成 | turn 结束自检 | 再次激活 planning 门禁，不能沿用 done Plan 写入 | 状态机单测 |
| AC-16 | 旧会话仅有 Goal、无 Plan | 解码并恢复 | 解码成功并进入 planning，写级工具被拒绝 | 旧 fixture 兼容测试 |
| AC-17 | 旧会话 Plan 为 approved/executing | 解码并恢复 | 解码成功并继续原 Plan，不重复确认 | 旧 fixture 兼容测试 |
| AC-18 | 普通 Plan 模式会话 | 完成提案、批准、progress 更新 | 行为与改动前一致 | 回归集成测试 |
| AC-19 | danger-tier 操作处于 approved Goal Plan | 请求执行 | 仍要求用户逐次确认 | 权限回归测试 |
| AC-20 | 新状态/报告持久化后重启 | 恢复运行 | 阶段、成员错误、报告、Plan 状态不丢失；不确定状态默认收紧权限 | 编解码/恢复测试 |

## 8. 发布与文档要求

- 新功能版本统一为 `1.189.0-rc1`，由 Goal Lead 同步 Swift、Go、资源、服务端版本 header、CHANGELOG 与 Product Overview。
- 版本目录至少包含 Requirement Specification Card、PRD、Architecture Design、Test Plan、Acceptance、tasklist 和 INDEX；HTML Prototype 因复用现有卡片明确标为 N/A。
- GT-001/GT-002 只有在开发成员完成代码落点核对、测试成员/需求成员完成独立验证后才能标记 done。

## 9. 风险与待决策

| 风险/问题 | 默认决定 | 后续责任方 |
| --- | --- | --- |
| 内置 `spawn_agent` 与现有会诊外部 CLI 的实现选择 | 使用统一的“独立只读规划成员”协议，不在 PRD 锁定供应商 | Architecture Design |
| 少于两份报告时用户是否可强行继续 | 本版不允许进入 proposed，避免确认 UI 变成绕过安全门槛的后门 | Goal Lead / 后续版本评审 |
| Teams 表信息量较大 | 字段完整性优先；呈现可折叠但不可丢字段 | UI/开发成员 |
| 旧 approved Plan 是否重新规划 | 尊重既有用户授权并继续；Plan 结束且 Goal 未完成时才重新规划 | 开发与测试成员 |
