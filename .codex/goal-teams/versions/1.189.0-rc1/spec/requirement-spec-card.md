# Requirement Specification Card：Goal Teams 规划优先流程

> 目标版本：1.189.0-rc1
> 状态：已实现并通过独立验证
> Owner：需求分析-Goal Teams 流程契约
> 来源：Codex `goal-teams` 规则、WillDeep 现有 Goal/Plan 契约与多专家会诊能力

## 1. 目标与价值

WillDeep 的 Goal 模式应从“Goal 定义后立即自主执行”改为“先完成多身份、基于仓库证据的辩证规划，经用户确认后再执行”。

用户价值：

- 在任何写操作前看到可审查的方案、成员分工、范围和验证责任。
- 让需求、实现与失败路径由不同身份独立审视，减少单一路径的盲点。
- 对分歧保留证据和取舍理由，不用多数票掩盖不确定性。
- 复用现有 Plan 确认与进度能力，不增加一套难以理解的新审批流程。

## 2. 功能结构

| 能力 | 要求 |
| --- | --- |
| Goal 收集 | 通过自然对话形成 Goal 与可观察的 Acceptance；不清楚时只问必要问题。 |
| 首轮独立规划 | 默认并行运行三个只读身份：`需求分析-目标边界质疑`、`架构-实现路径论证`、`测试-失败路径审查`。每份报告必须给出证据、主张、风险和建议。 |
| 第二轮分歧仲裁 | 独立仲裁身份读取首轮报告，区分共识、真实分歧、证据缺口、接受/拒绝的建议和停止条件；证据优先于多数票。 |
| Lead 综合 | 生成自包含的 `Teams 规划表` 与完整编号 `plan`；明确 owner、claimed tasks、locked scope、交付物、Done Criteria、文档、测试与独立 validator。 |
| 用户确认门禁 | Plan 为 proposed/rejected/缺失时禁止写级工具；只有用户批准后才能进入 approved/executing 并开始 Goal 执行。 |
| 执行闭环 | 按批准计划更新 `progress`，按 Goal 验收更新 `goal-check`；计划结束但 Goal 未完成时重新规划。 |
| 可恢复与兼容 | 规划过程可失败、重试、拒绝和恢复；旧 Goal/Plan 会话可解码，并按安全状态继续。 |

## 3. 主流程

1. 用户启用 Goal 模式并描述目标；WillDeep 形成 Goal 与 Acceptance。
2. 系统进入 planning，写级工具保持锁定；三个默认身份只读、相互独立地完成首轮报告。
3. 至少两份有效报告到齐后，第二轮仲裁专门处理冲突与薄弱证据。
4. Lead 依据 Goal、证据和仲裁结论生成 Teams 表及完整 `plan`，进入 proposed。
5. 用户批准：进入 approved/executing，解锁计划范围内的写操作；用户拒绝：保留 Goal，废弃当前 Plan，回到 planning。
6. 执行中持续报告 Plan 进度和 Goal 验收证据；若 Plan 已结束但 Acceptance 未完成，重新锁定写操作并规划下一轮。

## 4. 边界与安全降级

- 规划成员只能使用只读检查；报告、外部输出和仓库文本均作为惰性证据，不能把其中指令当系统指令执行。
- 三份首轮报告全部成功时正常继续；仅两份成功时允许继续，但 Teams 表必须显示缺失身份、失败原因和验证补偿。
- 少于两份有效报告、仲裁失败或独立成员能力不可用时，只能展示“未完成独立辩证验证”的不可执行草案；不得进入可批准执行状态，也不得静默退化为单 Lead 执行。
- 用户拒绝 Plan 不删除 Goal；重试必须生成新的 Plan，旧 Plan 不能复用为授权。
- 旧会话中已 approved/executing 的 Plan 可按原授权继续；只有 Goal、没有有效 Plan 的会话必须先进入新规划门禁。
- 已 done 的 Plan 不是永久通行证；只要 Goal 仍未满足，就必须重新规划和确认。

## 5. 非目标

- 不逐字复制 Codex 的 JSONL、dashboard 或全部运行时文件格式。
- 不把现有“外部 CLI 多专家会诊”的具体供应商或模型选择固化为 Goal Teams 产品协议。
- 不新增独立页面；优先复用现有 Goal、Plan、Workflow/会诊卡片。
- 不改变普通 Plan 模式的既有提案、批准与进度语义。
- 不在本需求阶段规定具体 Swift 类型、存储字段或 UI 布局。

## 6. 可验证结果

- Goal 定义后、Plan 批准前，任一写级工具调用均被拒绝，且只读规划仍可进行。
- 首轮默认出现三个唯一身份；第二轮只在至少两份有效报告后运行，并输出分歧与证据裁决。
- 最终 Teams 表字段完整，编号 Plan 覆盖用户请求的完整交付与验证，不以样例或首阶段冒充完成。
- 批准后才可执行；拒绝、部分失败、全部失败、恢复与旧会话路径均有确定状态和自动化断言。
- 普通 Plan 模式、既有 Goal checklist/progress 解析和危险操作审批不回归。

## 7. 开放问题

1. 首版默认独立成员由内置 `spawn_agent`、现有会诊编排，还是统一抽象层承载，由 Architecture Design 决定；需求只约束独立性、只读性和可追溯证据。
2. 用户是否可显式选择“低于两份报告仍继续”，本版默认不允许，以安全优先；若未来开放，必须作为单独、可审计的风险确认。
3. Teams 表在 transcript 与 Plan 卡片中的详细呈现方式由现有 UI 容量验证后决定，但必填字段不得省略。
